# Design: VLESS через Яндекс CDN (XHTTP, packet-up, uplink GET)

## Overview

Каскад из брифа ложится на уже существующую модель мультиплексора, а не заменяет её: Caddy L4
по-прежнему владеет `:443` и решает по SNI, а разбор пути происходит внутри — там же, где
сегодня живут decoy-сайты протоколов.

```
клиент ──► cdn.<домен>:443 ──► Yandex CDN edge
                                    │  origin_protocol=https, origin SNI
                                    ▼
                          :443 на нашем сервере
                                    │
                      Caddy L4 (SNI-мультиплексор)
                                    │ match tls.sni = origin-имя
                                    │ handler tls  → расшифрованный поток (h1 / h2c)
                                    ▼
                 127.0.0.1:<decoy_port>  локальный Caddy HTTP server
                 listener_wrapper PROXY v2, protocols h1 + h2c
                                    │
                     ┌──────────────┴───────────────┐
                     │                              │
        path = XHTTP-путь                    все остальные пути
                     │                              │
        127.0.0.1:<core_port>              сгенерированная страница
        sing-box: VLESS + XHTTP                     (file_server)
        packet-up, uplink GET
```

## Decision D1 — Пользоваться существующим `http_path_proxy`, научив внутренний сервер h2c

Выбран **минимально инвазивный** вариант, как и требовалось: маршрут остаётся
`route_kind: "http_path_proxy"`, владение `:443` и модель SNI-роутинга не меняются. Дополнения:

1. у L4-маршрута origin-имени явно объявляется ALPN `h2` и `http/1.1`, чтобы CDN мог идти по h2;
2. внутренний Caddy HTTP server, обслуживающий этот маршрут, получает
   `protocols: ["h1", "h2c"]` — он должен принимать уже расшифрованный поток и как HTTP/1.1,
   и как cleartext HTTP/2;
3. PROXY v2 остаётся включённым (`listener_wrappers`) — иначе сломается определение реального
   адреса клиента.

**Проверено по документации Caddy:** поле `protocols` принимает `h1|h2|h2c|h3`, и при включении
`h2c` обязателен `h1` (ограничение Go). `h2c` не входит в дефолт (`h1 h2 h3`) именно потому,
что он не шифрован — то есть включать его надо осознанно. caddy-l4 после терминирования TLS
отдаёт согласованный ALPN как `l4.tls.proto`.

**Проверено по исходникам ядра, а не по памяти:** в нашем ядре `packet-up` — единственный режим,
в котором допустим `uplink_http_method = "GET"`; размещение uplink-данных тоже разрешено только
там; `x_padding_bytes` нельзя отключить.

**Альтернатива (вариант B), сознательно не выбранная:** отдать origin целиком HTTP-приложению
Caddy и не иметь внутреннего перехода. Она убирает один локальный хоп, но переносит маршрутизацию
путей в другой слой и меняет то, кто владеет SNI-маршрутом, — то есть ровно то, чего просили
избежать. Вернуться к ней можно только если вариант A не пройдёт живую проверку (D9) и при
условии, что итоговая конфигурация окажется проще, а не просто короче на один хоп.

## Decision D2 — Один источник значений для маршрута

Путь, имена и порт живут в состоянии протокола и попадают во все три места из одного источника:

| Значение | Куда попадает | Проверка |
| --- | --- | --- |
| `origin_host` | SNI-match L4, сертификат, имя бэкенда | обязано совпасть с сертификатом |
| `cdn_domain` | только клиентский профиль и документация | не участвует в серверном конфиге |
| `xhttp_path` | web-маршрут, inbound ядра, клиентский профиль | минимум 3 сегмента, без пробелов, начинается с `/` |
| `core_port` | локальный reverse_proxy и inbound ядра | свободный порт на `127.0.0.1` |
| `decoy_root` | каталог сайта | существующая проверка `/var/www/decoy-*` |

Существующие проверки в `sni_router_planning.py` переиспользуются, а не дублируются.

## Decision D3 — Профиль XHTTP: бриф → реальные поля ядра

Имена из брифа — Xray-style; ниже фактическое соответствие в том ядре, которое установлено.

| Из брифа | Поле ядра | Значение |
| --- | --- | --- |
| `mode: packet-up` | `mode` | `packet-up` |
| `uplinkHTTPMethod: GET` | `uplink_http_method` | `GET` (законно только в `packet-up`) |
| `path` | `path` | из состояния |
| `host` | `host` | origin-имя |
| `xPaddingBytes: 100-1000` | `x_padding_bytes` | `"100-1000"` |
| `xPaddingObfsMode: true` | `x_padding_obfs_mode` | `true` |
| `xPaddingKey: hash` | `x_padding_key` | `"hash"` |
| `xPaddingHeader: X-Client-Version` | `x_padding_header` | `"X-Client-Version"` |
| `xPaddingPlacement: queryInHeader` | `x_padding_placement` | `queryInHeader` |
| `xPaddingMethod: tokenish` | `x_padding_method` | `tokenish` |
| `sessionIDPlacement: header` | `session_placement` | `header` |
| `sessionIDKey: X-Upload-Token` | `session_key` | `"X-Upload-Token"` |
| `sessionIDTable: Base62` | `session_id_table` | `Base62` |
| `sessionIDLength: 16-32` | `session_id_length` | `"16-32"` |
| `seqPlacement: query` | `seq_placement` | `query` |
| `seqKey: chunk_id` | `seq_key` | `"chunk_id"` |
| `uplinkDataPlacement: body` | `uplink_data_placement` | `body` (только `packet-up`) |
| `scMaxEachPostBytes: 131072-1048576` | `sc_max_each_post_bytes` | `"131072-1048576"` |
| `scMaxBufferedPosts: 30` | `sc_max_buffered_posts` | `30` |
| `scMinPostsIntervalMs: 50-150` | `sc_min_posts_interval_ms` | `"50-150"` |
| `noSSEHeader: false` | `no_sse_header` | `false` |
| `noGRPCHeader: false` | `no_grpc_header` | `false` |
| `XMUX.enabled: true` | `xmux` | блок ниже |
| `XMUX.maxConcurrency: 16-32` | `xmux.max_concurrency` | `"16-32"` |
| `XMUX.maxConnections: 0` | `xmux.max_connections` | `0` |
| `XMUX.cMaxReuseTimes: 1000` | `xmux.c_max_reuse_times` | `1000` |
| `XMUX.hMaxRequestTimes: 600-900` | `xmux.h_max_request_times` | `"600-900"` |
| `XMUX.hMaxReusableSecs: 100` | `xmux.h_max_reusable_secs` | `100` |

**Три решения, принятые осознанно, а не скопированные:**

1. **`hKeepAlivePeriod: 20000` не переносим.** В нашем ядре поле читается как
   `time.Duration(HKeepAlivePeriod) * time.Second` и зажимается в диапазон 5 с – 5 мин со
   значением по умолчанию 30 с. В референсе это Xray-шные миллисекунды; перенос дал бы 20 000
   секунд и всё равно схлопнулся бы в 5 минут. Поле не задаётся — ядро берёт 30 с, что для h2
   keep-alive разумно. Решение фиксируется в дизайне и в release-заметках.
2. **`sc_stream_up_server_secs` не задаётся** в `packet-up`: по смыслу оно относится к
   `stream-up`. Значение из брифа (20–80) применимо в другом режиме.
3. **`congestion_controller` / `cwnd` не задаются** — они относятся только к HTTP/3, а мы
   работаем по h2.

Дополнительно: `trusted_x_forwarded_for` оставляем пустым (адрес клиента приходит через PROXY v2,
а адреса edge-узлов CDN не фиксированы), `server_max_header_bytes` — `8192` как в upstream-примере.

## Decision D4 — VLESS Encryption: ключи генерирует HYDRA

Поддержка подтверждена по исходникам выпущенного ядра: серверная часть инициализируется из поля
`decryption` inbound'а, клиентская включается полем `encryption` в outbound.

Формат, разобранный из парсеров ядра:

- сервер: `mlkem768x25519plus.<native|xorpub|random>.<from>[-<to>]s.<приватный ключ base64url>`
- клиент: `mlkem768x25519plus.<native|xorpub|random>.<1rtt|0rtt>.<публичный ключ base64url>`

Решение: HYDRA генерирует X25519-пару криптостойким RNG (32 байта; парсер ядра принимает и
x25519, и ML-KEM-768 — X25519 достаточно), приватный ключ уходит в `decryption`, публичный — в
клиентский профиль. Используется режим рукопожатия `1rtt` (у `0rtt` серверная сторона может
ответить «0-RTT is not allowed»). Окно времени задаётся широким, чтобы ротация ключа была
управляемой: при смене ключа старый остаётся в окне действия до истечения. Приватный ключ
хранится как секрет, рядом с остальными учётными данными.

## Decision D5 — Сайт: статическая генерация по таймеру, а не демон

Требование «настоящий динамический сайт» закрывается генерацией страницы, а не файлом-заглушкой:

- генератор запускается systemd-таймером каждые 10 минут и пишет страницу в существующий
  decoy-каталог; Caddy продолжает отдавать её как обычно (`file_server`) — нового демона и
  нового класса отказов не появляется;
- **погода** берётся у Open-Meteo при генерации, с таймаутом; результат кешируется, а при
  неудаче сохраняются последние удачные значения и страница показывает нейтральное состояние;
- **время** считается в браузере: в страницу попадают IANA-идентификаторы зон, а живое время
  рисует маленький встроенный скрипт через `Intl.DateTimeFormat`. Внешний API времени не
  используется вообще, поэтому «замороженных» часов не бывает;
- **изображение региона** обновляется раз в 12 часов отдельным заданием, хранится локально и
  отдаётся локально; при неудаче остаётся последняя удачная копия, при первом запуске —
  встроенный запасной файл. Источник выбирается с лицензией, допускающей автоматическую загрузку
  и повторную отдачу; источник и атрибуция фиксируются в подвале страницы.
- Метаданные региона берутся тем же источником, что и флаг в меню HYDRA: провайдер
  `ipwho.is`, к которому уже ходит `hydra/services/security_intel.py` (кеш
  `/var/lib/hydra/ip-intel-cache.json`, TTL 7 дней, fail-open). Один ответ отдаёт страну,
  город, столицу, координаты и IANA-зону; сейчас из него берётся только подмножество
  (код страны, флаг, владелец, ASN), поэтому выборка расширяется — новых зависимостей и
  локальных таблиц не появляется.
- Заголовок страницы — **город сервера**, столица страны идёт отдельной строкой.
- Погода берётся по координатам этого города, время считается по его IANA-зоне локально.

Содержимое страницы — регион, столица, изображение, погода, часы по нескольким зонам, дата,
подвал со статусом. Ничего из этого не зависит от IP посетителя.

## Decision D6 — Сертификат origin выпускает существующий сервис

Origin-имя обслуживается тем же механизмом, что и остальные домены: `certbot` с HTTP-01 и
временно освобождаемым `:80` (`hydra/services/certificates.py`), файлы в
`/etc/letsencrypt/live/<origin>/`. Caddy получает пару `cert_file`/`key_file` через уже
существующий путь `_tls_app`, который включает backend'ы с `route_kind: http_path_proxy`.
Собственный ACME Caddy не используется.

Требование к окружению: A-запись origin-имени на сервер. Без неё HTTP-01 не проходим.

## Decision D7 — Новый плагин, переиспользующий существующие примитивы

Плагин `hydra/plugins/vless_cdn/` добавляется рядом с существующим `vless_xhttp/`, а не внутрь
него: у него другая топология (своё origin-имя и сертификат, разделение путей, сайт), и менять
поведение уже работающего протокола VLESS+XHTTP ради нового сценария не нужно.

Переиспользуется: планирование и генерация SNI-документа (`sni_router_planning`,
`sni_router_document`, `sni_router_http`), профиль XHTTP и подбор значений (`vless_xhttp.tuning`,
`vless_xhttp.presets`), выпуск сертификата (`hydra/services/certificates.py`), клиентский
рендер и share-данные (`vless_xhttp.client`).

Добавляется: генератор страницы, сервис погоды с кешем, задание на изображение, установка
маршрута origin и inbound'а, выдача клиентского профиля.

## Decision D8 — Маршрутизация и защита от перехвата

Внутренний сервер обслуживает пути строго в этом порядке:

| Путь | Обработчик | Примечание |
| --- | --- | --- |
| XHTTP-путь (и его подпути) | `reverse_proxy` → `127.0.0.1:<core_port>` | без кеша, без буферизации, без малого лимита тела, `Host` передаётся |
| `/assets/*` | `file_server` | обычное кеширование |
| всё остальное, включая `/` | сгенерированная страница | никогда не перехватывает XHTTP-путь |

Правило «любой путь → туннель» запрещено. Совпадение XHTTP-пути с путём сайта считается ошибкой
конфигурации и проверяется тестом, а не глазами.

## Data model

Состояние протокола (дополняет существующую схему, миграции — как принято в проекте):

| Поле | Тип | Назначение |
| --- | --- | --- |
| `cdn_domain` | str | публичное имя для клиента |
| `origin_host` | str | имя для SNI и сертификата |
| `xhttp_path` | str | единый путь для web, ядра и клиента |
| `core_port` | int | локальный порт inbound'а |
| `uuid` | str | пользователь VLESS |
| `encryption_private_key` / `encryption_public_key` | str | пара для VLESS Encryption (секрет / публичная часть) |
| `encryption_mode` | str | `native` по умолчанию |
| `region` | dict | страна, столица, координаты, зоны, идентификатор изображения |

## Interfaces

- Установка спрашивает `cdn_domain` и `origin_host`, показывает план до применения и итог после.
- Статус протокола показывает: CDN-домен, origin-имя, путь, порт ядра, срок сертификата,
  время последней удачной погоды и изображения.
- Выдача клиента: native JSON, плюс share-данные, если они корректно выражают выбранный профиль.
- Отдельная команда обновления страницы/изображения — чтобы оператор мог не ждать таймера.

## Failure handling

| Отказ | Поведение | Откат |
| --- | --- | --- |
| Certbot не смог выпустить сертификат | установка останавливается до записи маршрута | состояние не изменено |
| Ядро отвергло конфигурацию inbound'а | маршрут не публикуется | предыдущий JSON ядра |
| Погодный API недоступен или таймаут | страница без погоды, значения из кеша | последняя удачная страница |
| Обновление изображения не удалось | остаётся прошлая копия | встроенный запасной файл |
| `caddy-l4` не принимает конфигурацию | перезагрузка не выполняется | предыдущий рабочий JSON |
| h2c в живом тесте не работает | вариант A признаётся несостоятельным | переключение на вариант B (D1) |

## Testing strategy

**Модульные:** рендер маршрута и внутреннего сервера (наличие `protocols: ["h1","h2c"]`,
PROXY v2, порядок путей, отсутствие кеша на XHTTP), формирование inbound'а (все поля таблицы D3),
генерация пары ключей и обеих строк шифрования, сборка клиентского профиля, страница при
недоступной погоде, выбор зон, атрибуция изображения, миграция состояния.

**Конфигурационные:** сгенерированный документ проверяется валидатором Caddy; JSON ядра —
разбором самим ядром. Проверка, что XHTTP-путь не отдаётся сайтом.

**Живые:** раздел D9.

## Decision D9 — Живая проверка варианта A (обязательный гейт)

Пока это не пройдено, протокол не считается готовым:

1. собрать конфигурацию на выделенном сервере, проверить её валидатором Caddy;
2. поднять реальный клиент с ядром, собранным из нашего релиза, с профилем `packet-up` и
   `uplink_http_method: GET`;
3. убедиться по логам, что ALPN согласован как `h2` и что внутренний сервер принял поток по
   `h2c` (а не откатился на HTTP/1.1 по ошибке);
4. убедиться, что PROXY v2 работает: реальный адрес клиента доходит до ядра и до страницы;
5. открыть сайт обычным браузером — страница отдаётся, XHTTP-путь страницу не отдаёт никогда;
6. зафиксировать результат: скорость, отсутствие обрывов на длинных соединениях, поведение при
   переподключении.

Если пункт 3 или 4 не проходит — вариант A отклоняется, и только тогда рассматривается вариант B
с отдельной проверкой и обоснованием, что итоговая конфигурация действительно проще.

## Bugfix extension — Host, lifecycle и identity (2026-09-18)

### D10 — Публичный CDN-host является единым XHTTP host

Живой конфиг доказал расхождение: Caddy отправляет `Host: cdn_domain`, а inbound
`vless-cdn-in` сконфигурирован с `transport.host: origin_host`. Поэтому после устранения
TLS-ошибки XHTTP получает корректный h2c-запрос с чужим host и отвечает `Not Found`.

**Решение:** `cdn_domain` — единственное значение XHTTP `host` для client profile, Caddy
reverse-proxy и server inbound. `origin_host` остаётся исключительно в TLS/SNI-маршруте,
сертификате и L4 backend. Меняется канонический владелец inbound (`VlessCdnPlugin.configure`),
не Caddy-рендер и не клиент.

### D11 — CDN-имя не наследует family override обычного VLESS

`tag_client_link()` правильно распознаёт CDN через функциональный маркер
`extra.uplinkHTTPMethod=GET` и выбирает ключ `vless:cdn`. Ошибка возникает на следующем шаге:
для этого ключа передаётся `base_key="vless"`, поэтому общий resolver превращает override
обычного VLESS в частично унаследованное имя с суффиксом ` CDN`.

**Решение:** для `vless:cdn` резолвить только точный ключ и встроенный default
`<email> VLESS Яндекс CDN`; `base_key` и `base_suffix` не передавать. Общий
`resolve_configuration_name()` не меняется: fallback остаётся для вариантов, где он является
контрактом (Naive QUIC, AWG desktop/mobile). Точный global/user override `vless:cdn` сохраняется.

> **Супerseded by D13 (2026-09-19):** сам lookup-ключ `vless:cdn` оказался ошибкой — он не совпадает
> с каноническим именем плагина `vless_cdn`, под которым UI и HydraBox хранят переименование.
> Механика «только точный ключ, без family fallback» из этого решения остаётся в силе; меняется
> имя ключа. См. D13 ниже.

### D12 — Lifecycle принадлежит application use-case, не TUI

Аудит обнаружил, что специальное меню напрямую вызывает provisioning и systemd-операции, а
при удалении убирает таймер до транзакционного `uninstall`. Это нарушает application boundary;
провал apply оставляет полусостояние, а non-TUI removal может оставить сиротский timer.

**Решение:** расширить существующий `hydra.services.vless_cdn_install` отдельной операцией
провижининга/удаления и передать её через `ApplicationService` как application port. Новый
универсальный lifecycle-framework или новый persisted state не создаются. Плагин остаётся
чистым: только validation/config/client hooks, без systemd и сервисных импортов.

Операция владеет полным snapshot desired state и следующими компенсациями:

1. сертификат выпускается до изменения desired state;
2. изменение протокола, `activate` и apply выполняются как один use-case;
3. timer и первая страница создаются только для staged CDN-конфига;
4. любой провал после staging восстанавливает snapshot, прежний runtime-config и timer;
5. удаление удаляет timer только внутри той же операции; если cleanup не проходит, операция
   восстанавливает snapshot/runtime и не сообщает об успешном удалении.

### Regression plan

- inbound, Caddy и клиентский profile имеют одинаковый CDN XHTTP host;
- обычный `vless` override не меняет CDN-имя; точный `vless:cdn` override меняет только CDN;
- provisioning, apply, timer/page и uninstall покрыты failure-injection тестами, включая rollback;
- generic lifecycle и другие протоколы не получают новых импортов, портов, маршрутов или имён.

> Decision CLI: `scripts/decisions.mjs` в проекте отсутствует, поэтому ADR-light создать
> штатной командой здесь невозможно. Решение зафиксировано в этой design extension.

## Bugfix extension — один ключ имени для CDN-профиля (2026-09-19)

### Проверенная картина расхождения

| Факт | Доказательство |
| --- | --- |
| Переименование в UI пишется под каноническим plugin key `vless_cdn` | `hydra/ui/_menus/users_links.py:133-155` через `configuration_name_key()` (`hydra/core/configuration_names.py:63-70`) |
| HydraBox читает тот же `vless_cdn` | `hydra/services/subscriptions/hydrabox.py:292-297` |
| URI-подписка читает другой ключ `vless:cdn` | `hydra/services/subscriptions/links.py:116-126`, `:153-166` |
| CDN распознаётся функциональным маркером `extra.uplinkHTTPMethod` | `hydra/services/subscriptions/links.py:66-86` |
| Встроенный публичный label | `CLIENT_LABEL = "VLESS Яндекс CDN"` в `hydra/contracts/vless_cdn.py:21` |

Следствие: override `vless_cdn: "Обход БС"` виден в HydraBox и в native JSON, но не виден в
URI-подписке — Throne и NekoBox падают в default `<email> VLESS Яндекс CDN`. Коммит `7af2cb2`
ввёл `vless:cdn` как *lookup*-ключ и никогда не был согласован с каноническим именем плагина;
`14784c6` убрал family-fallback, закрепив расхождение.

### D13 — Резолвер URI-подписки использует канонический ключ плагина

`_configuration_name_key()` для распознанного CDN VLESS возвращает `vless_cdn` вместо `vless:cdn`.
Больше ничего не меняется:

- распознавание остаётся функциональным (`extra.uplinkHTTPMethod`), а не по имени хоста;
- обычный VLESS XHTTP продолжает резолвиться под ключом `vless`, family-fallback для него не
  трогается;
- `resolve_configuration_name()` не меняется — меняется только ключ, под которым вызывается;
- HydraBox, native JSON и UI уже используют `vless_cdn`, поэтому не меняются вообще.

**Ловушка, которую нельзя пропустить:** в `tag_client_link()` рядом стоит
`base_key = "" if key == "vless:cdn" else key.partition(":")[0]`. Если поменять только строку
ключа, это условие перестанет совпадать, `base_key` станет `"vless"` и family-override обычного
VLESS снова начнёт накрывать CDN-профиль — то есть вернётся ровно тот дефект, который чинил
`14784c6`. Обе строки меняются одним диффом, и регрессионный тест
`test_a_family_override_still_keeps_the_cdn_profile_apart` обязан остаться зелёным.

Почему не наоборот (не переучить UI и HydraBox на `vless:cdn`): ключ `vless:cdn` **никогда не был
доступен для записи** — ни один поддерживаемый путь его не сохраняет, он существовал только как
lookup-строка внутри `links.py` и в двух тестах. `vless_cdn` — это имя плагина, оно уже лежит в
`state.json`, в журнале решений и в JSON-профиле. Менять читателя дешевле и безопаснее, чем
переписывать уже сохранённые данные и три вызывающих слоя.

### D14 — Миграции нет, и это проверяемо

`state.json` не переписывается: `SCHEMA_VERSION` не меняется, `configuration_names` остаётся
плоским словарём строк, ключ `vless_cdn` уже канонический. Побочное следствие фиксируется честно:
override, вручную вписанный в state как `vless:cdn`, после фикса перестанет применяться —
профиль вернётся к встроенному default и переименовывается из UI одной командой. Отдельный
legacy-alias не добавляется: код для ключа, который нельзя было установить ни одним штатным
способом, — это мёртвая ветка, а не совместимость.

### Регрессионный план

- один global override `vless_cdn` даёт одинаковое имя в URI fragment и в HydraBox profile name
  (сквозной тест, а не два изолированных);
- один user override `vless_cdn` даёт тот же результат и не затрагивает другого пользователя;
- override `vless` меняет только обычный VLESS XHTTP, `vless_cdn` — только CDN;
- без override URI сохраняет прежний default `<email> VLESS Яндекс CDN`, HydraBox — прежний
  `subscription_profile_name`;
- тест «ровно один профиль на CDN» продолжает падать, если два VLESS-профиля снова сольются в имя.
