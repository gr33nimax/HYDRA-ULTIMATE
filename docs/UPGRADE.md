# Установка и обновление

Документ описывает два разных и не взаимозаменяемых сценария развёртывания.

| Сценарий | Инструмент | Когда применять |
| :--- | :--- | :--- |
| Чистая установка | `bootstrap.sh` | На VPS ещё нет HYDRA |
| Обновление рабочей установки | `updater.sh` | HYDRA уже установлена и обслуживает трафик |

> [!CAUTION]
> Не запускайте `bootstrap.sh` поверх работающей установки и не обновляйтесь
> через `git pull`: это может повредить данные. Рабочую VPS обновляет
> только `updater.sh`.

## Требования

- Ubuntu 22.04+ или Debian 12+ с systemd;
- Python 3.10+;
- от 512 МБ RAM и 2 ГБ диска (для обновления — место под второй release);
- внешний IPv4, права `root` и доступ к GitHub.

Установщик проверяет ОС, версию Python и права; ресурсы и IPv4 он не измеряет.

## Чистая установка

```bash
curl -fsSL https://raw.githubusercontent.com/gr33nimax/HYDRA-ULTIMATE/main/bootstrap.sh | sudo bash
```

Установщик:

- проверяет систему и ставит зависимости;
- ставит Hydracore (канал `stable`, с проверкой SHA-256); уже установленное или
  стороннее ядро не трогает;
- разворачивает код в `/opt/hydra`, создаёт изолированное `.venv` и команду `hydra`;
- ставит `certbot` заранее, до первой активации TLS-транспорта.

Журнал — `/var/log/hydra/install.log`. Ветку задаёт `HYDRA_REF` (по умолчанию
`main`). Caddy L4 и конкретные протоколы активируются только при включении
соответствующих модулей. При ошибке установщик возвращает предыдущий checkout
и каталог установки.

### Запуск из исходников

Режим для разработки и отладки:

```bash
git clone -b main https://github.com/gr33nimax/HYDRA-ULTIMATE /opt/hydra
cd /opt/hydra
sudo apt-get install -y python3-venv
sudo python3 -m venv .venv
sudo .venv/bin/python -m pip install --upgrade pip
sudo .venv/bin/python -m pip install -r requirements.lock
sudo .venv/bin/python main.py
```

> [!WARNING]
> Не запускайте исходники системным `python3`: в этом режиме зависимости из
> `requirements.lock` не устанавливаются.

### Первичная настройка

Включите нужные протоколы и системные службы в TUI, создайте пользователей, затем
проверьте состояние:

```bash
hydra status
hydra check
```

## Обновление рабочей VPS

`updater.sh` даёт одну публичную команду обновления. Он полностью загружает
`upgrade.sh` во временный файл и только после этого запускает транзакционное
ядро, которое выполняет переход на точный SHA указанной ветки.

### Ход обновления

```text
   этап                                состояние рабочей установки
   ──────────────────────────────────────────────────────────────────────
1  проверка установленной версии       работает, трафик идёт
2  разрешение SHA под блокировкой      работает, трафик идёт
3  сборка release + .venv рядом        работает, трафик идёт
4  read-only preflight новым кодом,    работает, трафик идёт
   запоминание активных units
   ─────────────────── точка невозврата ───────────────────
5  сырой state + wrapper, проверенный  helper-службы HYDRA остановлены;
   backup, импорт legacy state         связанный Caddy L4 временно остановлен
6  переключение симлинка /opt/hydra,   работает на новой версии
   общие resource defaults, запуск
   ранее активных units
7  итоговая проверка: check, status,   работает на новой версии;
   systemd, уборка старых артефактов   лишние releases и снимки удаляются
   ──────────────────────────────────────────────────────────────────────
```

Этапы 1–4 полностью безопасны: они ничего не меняют в рабочей установке, и
прерывание на них не оставляет следов. Начиная с этапа 5 действует откат.

```text
   сбой на 5–7 ──▶ откат в строгом порядке:

        остановить новый runtime
             ▼
        вернуть сырой state snapshot      ◀── обязательно раньше кода
             ▼
        вернуть код и wrapper
             ▼
        запустить units из active-units.txt
```

Порядок принципиален: старый код не должен увидеть state нового формата.

### Что гарантирует updater

- Новый release и `.venv` собираются отдельно; до точки невозврата новый код
  проходит read-only preflight на действующем state.
- Перед переключением сохраняются сырой `/var/lib/hydra`, wrapper `hydra` и
  проверенный backup с манифестом и SHA-256.
- Перенос state сохраняет лимиты, отпечатки устройств, credentials, Telegram-токены,
  сетевые секреты и настройки плагинов.
- Переключение на новый release атомарно; ранее активные службы (включая Caddy L4)
  останавливаются и запускаются снова, потом идёт повторная проверка.
- Любой сбой после точки невозврата откатывает state, код, wrapper и службы.

Порядок этапов, состав снимка отката и внутренние гарантии — в
[ARCHITECTURE.md](ARCHITECTURE.md).

После успешного обновления updater оставляет текущий release и
`HYDRA_KEEP_RELEASES-1` предыдущих (по умолчанию 3), снимки отката моложе
`HYDRA_KEEP_BACKUP_DAYS` дней (по умолчанию 7). Текущий release не удаляется
никогда, а сбой уборки не влияет на результат.

### Перед запуском

- Установка должна находиться в `/opt/hydra`.
- В Git checkout не должно быть локальных изменений — updater намеренно
  завершится с ошибкой, если они есть.
- Не запускайте одновременно TUI, изменяющие CLI-команды или второй updater.

```bash
hydra check
sudo hydra upgrade check
sudo git -C /opt/hydra status --short
```

Последняя команда не должна ничего вывести.

### Запуск

```bash
curl -fsSL https://raw.githubusercontent.com/gr33nimax/HYDRA-ULTIMATE/main/updater.sh | sudo bash
```

Публичный launcher проверяет права, имя ветки и наличие команд, скачивает updater
engine и передаёт ему управление. SHA ветки разрешается один раз, и
устанавливается именно этот commit, даже если ветка сдвинется во время загрузки.

Вывод — на русском, нумерованными этапами и с цветом в терминале (`NO_COLOR=1`
отключает). После успеха печатается сводка: ветка, переход commit, снимок
отката и лог.

| Переменная | По умолчанию | Назначение |
| :--- | :--- | :--- |
| `HYDRA_REF` | `main` | Ветка, чей точный SHA нужно установить |
| `HYDRA_REPO_URL` | официальный репозиторий | Git remote |
| `HYDRA_INSTALL_DIR` | `/opt/hydra` | Стабильная точка входа установки |
| `HYDRA_RELEASES_DIR` | `/opt/hydra-releases` | Каталог изолированных release |
| `HYDRA_UPGRADE_BACKUP_DIR` | `/var/backups/hydra/upgrades` | Постоянные снимки отката |
| `HYDRA_KEEP_RELEASES` | `3` | Сколько release остаётся после успешного обновления |
| `HYDRA_KEEP_BACKUP_DAYS` | `7` | Сколько дней хранятся снимки отката |
| `HYDRA_UPGRADE_LOCK_FILE` | `/run/lock/hydra-upgrade.lock` | Блокировка против одновременных обновлений |

### Длительность простоя

Кратковременно останавливаются службы и таймеры HYDRA. Если Caddy L4 зависит от
`hydra-caddy-source` или `hydra-source-relay`, updater также запоминает,
останавливает и затем восстанавливает `caddy-l4.service`. Sing-Box и независимые
прокси-процессы updater не заменяет. Для TLS-транспортов за Caddy возможна
короткая пауза на время legacy import state и переключения release.

Это возможно потому, что постоянные systemd units ссылаются на стабильный
`/opt/hydra` и интерпретатор `/opt/hydra/.venv/bin/python`, а не на физический
release-каталог: новый код и зависимости собираются до остановки процессов.

## Проверка результата

```bash
hydra check
hydra status
sudo systemctl --failed --no-pager
readlink -f /opt/hydra
```

Лог обновления — `/var/log/hydra/upgrade.log`. Сводка печатает каталог снимка
строкой `Снимок отката`; после неё идут путь к логу и напоминание о поддержке
проекта. Снимок содержит:

| Артефакт | Содержание |
| :--- | :--- |
| `metadata.env` | Исходный и целевой SHA |
| `state-before-upgrade/` | Сырой `/var/lib/hydra` до обновления |
| `hydra-backup.tar.gz` | Проверенный backup |
| `backup-verification.json` | Результат проверки этого backup |
| JSON-отчёты | Preflight, legacy import state и post-cutover проверки |
| `active-units.txt` | Службы и таймеры, активные до обновления |
| `SUCCESS` | Маркер полного завершения |

> [!TIP]
> Не удаляйте последний снимок до того, как проверите реальный трафик,
> подписки и клиентские подключения.

## Если обновление завершилось ошибкой

Не запускайте поверх ошибки `bootstrap.sh` и не делайте `git reset --hard`.
Сначала соберите факты:

```bash
sudo tail -n 200 /var/log/hydra/upgrade.log
sudo systemctl --failed --no-pager
hydra check
```

Обычная ошибка приводит к автоматическому откату. В каталоге снимка при этом
остаются неудачный release, state после сбоя и исходный state.
При ошибке updater также печатает название операции и путь к её JSON-отчёту.

Если автоматический откат не смог вернуть службу, восстанавливайте строго в этом
порядке:

1. остановить службы HYDRA;
2. вернуть `state-before-upgrade`;
3. вернуть прежний `/opt/hydra` и wrapper `hydra`;
4. выполнить `systemctl daemon-reload`;
5. запустить службы из `active-units.txt`.

Не удаляйте артефакты снимка до успешного восстановления.

## State Format и legacy import

State Format — **v1**, один на весь репозиторий
(`hydra/core/state_format.py`, `STATE_FORMAT_VERSION`), от ветки не зависит.
Обычное изменение Calls или другой feature не повышает `format_version` и не
добавляет migration script. State хранит только desired config; совместимость
transport/wire проверяется по runtime capabilities перед apply.

Один importer принимает любую плоскую schema 0–18 и сразу создаёт
State Format v1. Он сохраняет пользователей, credentials, Telegram-токены,
сетевые секреты, plugin state и kernel; Calls нормализуется в актуальный
`vk_parasite`. Импорт не меняет host binary, units или runtime.

Обновление подписочного renderer не меняет State Format и повторно использует
существующий per-user A256GCM key, но wire contract несовместим с HydraBox v1.
После обновления выдавайте ссылку заново: клиент HydraBox должен быть не ниже
`0.4.0-beta.1`, а fragment теперь называется `#hydra-key=…`. Сервер публикует
только Hydra Subscription v2; downgrade к v1 или plaintext fallback отсутствует.

qWDTT не создаёт creator-комнаты и не использует VK cookies: после обновления
удалите оставшиеся qWDTT creator units и Sync Agent, убедившись, что qWDTT
работает. Для Hydra VK Tunnel импортируйте локальный JSON cookies
в меню `Calls · VK` — это доступно до установки Calls; JSON валидируется до
атомарной замены `/etc/hydra/cookiesvk/cookies-vk.json` (`0600`). Затем Calls
сам создаёт и обслуживает пул ровно из 4 VK-комнат.
Отдельно импорт выполняет совместимая команда:

```bash
sudo hydra upgrade migrate-state
```

Имя `migrate-state` сохранено для upgrade-скриптов. Команда предназначена для
`upgrade.sh` и аварийных процедур. В обычной
эксплуатации вызывайте её только при остановленных процессах HYDRA и наличии
проверенного backup. Импорт идемпотентен: повторный вызов на актуальном формате
не переписывает state.

Запись импортированного документа выполняется атомарно. Неизвестная будущая
версия формата не считается повреждением и не заменяется старым backup: загрузка
завершается явной ошибкой совместимости.

Инварианты state и правила конкурентности — в
[ARCHITECTURE.md](ARCHITECTURE.md#6-state-и-рабочее-состояние).
