# Установка и обновление

Документ описывает два разных и не взаимозаменяемых сценария развёртывания.

| Сценарий | Инструмент | Когда применять |
| :--- | :--- | :--- |
| Чистая установка | `bootstrap.sh` | На VPS ещё нет HYDRA |
| Обновление рабочей установки | `upgrade.sh` | HYDRA уже установлена и обслуживает трафик |

> [!CAUTION]
> Не запускайте `bootstrap.sh` поверх работающей установки и не обновляйтесь
> вручную через `git pull`. Установщик не выполняет миграцию state под
> блокировкой, не квиесцирует фоновые процессы и не создаёт точку отката, а
> ручной `git pull` может дать старому коду state новой схемы.

## Требования

- Ubuntu 20.04+ или Debian 11+ с systemd;
- Python 3.10+;
- от 512 МБ RAM и 2 ГБ диска (для обновления — свободное место под второй
  release и отдельное виртуальное окружение);
- внешний IPv4 и права `root`;
- доступ к GitHub.

## Чистая установка

```bash
curl -fsSL https://raw.githubusercontent.com/gr33nimax/HYDRA-ULTIMATE/main/bootstrap.sh | sudo bash
```

Установщик проверяет права и систему, устанавливает зависимости и Sing-Box
Extended, разрешает точный commit выбранной ветки, разворачивает код в
`/opt/hydra`, создаёт изолированное Python-окружение и регистрирует команду
`hydra`. Журнал — `/var/log/hydra/install.log`.

Ветку можно выбрать переменной `HYDRA_REF` (по умолчанию `main`):

```bash
curl -fsSL https://raw.githubusercontent.com/gr33nimax/HYDRA-ULTIMATE/dev/bootstrap.sh \
  | sudo env HYDRA_REF=dev bash
```

Caddy L4 и конкретные протоколы активируются только при включении
соответствующих модулей. При ошибке установщик возвращает предыдущий checkout и
каталог установки.

### Запуск из исходников

Режим для разработки и отладки:

```bash
git clone -b main https://github.com/gr33nimax/HYDRA-ULTIMATE /opt/hydra
cd /opt/hydra
sudo apt-get install -y python3-venv
sudo python3 -m venv .venv
sudo .venv/bin/python -m pip install --upgrade pip
sudo .venv/bin/python -m pip install -r requirements.lock
sudo .venv/bin/python main.py
```

> [!WARNING]
> Не запускайте исходники системным `python3`: в этом режиме зависимости из
> `requirements.lock` (включая генератор QR-кодов) не устанавливаются.

### Первичная настройка

Включите нужные протоколы и системные службы в TUI, создайте пользователей, затем
проверьте состояние:

```bash
hydra status
hydra check
```

## Обновление рабочей VPS

`upgrade.sh` выполняет переход на точный SHA указанной ветки как единую
транзакцию.

### Что гарантирует updater

1. Под блокировкой определяется точный SHA целевой ветки.
2. Новый release и новое `.venv` собираются отдельно от `/opt/hydra`.
3. Новый код читает действующий state и выполняет `upgrade check`, `validate` и
   `plan` **без записи** (read-only preflight).
4. Запоминаются активные `hydra-*.service` и `hydra-*.timer`, после чего
   HYDRA-процессы временно останавливаются.
5. Сохраняются сырой `/var/lib/hydra`, wrapper команды `hydra` и проверенный
   backup с манифестом и SHA-256.
6. State атомарно мигрирует на актуальную схему. Лимиты и отпечатки устройств,
   credentials пользователей, Telegram-токены, сетевые секреты и настройки
   плагинов сохраняются.
7. `/opt/hydra` переключается на подготовленный release, ранее активные службы
   запускаются снова.
8. Выполняются повторные `validate`, `plan`, `status` и проверка systemd.

Ошибка после квиесцирования запускает откат в обратном порядке: новый runtime
останавливается, state возвращается в старую схему, затем возвращаются код и
wrapper, и только после этого запускаются ранее активные units. Порядок
принципиален — старый код не должен увидеть state новой схемы.

Старый release и backup после успешного обновления не удаляются.

### Перед запуском

- Установка должна находиться в `/opt/hydra`.
- В Git checkout не должно быть локальных изменений — updater намеренно
  завершится с ошибкой, если они есть.
- Не запускайте одновременно TUI, изменяющие CLI-команды или второй updater.

```bash
hydra check
sudo hydra upgrade check
sudo git -C /opt/hydra status --short
```

Последняя команда не должна ничего вывести.

### Запуск

```bash
(
  set -e
  upgrade_script=$(mktemp)
  trap 'rm -f "$upgrade_script"' EXIT
  curl -fsSL \
    https://raw.githubusercontent.com/gr33nimax/HYDRA-ULTIMATE/dev/upgrade.sh \
    -o "$upgrade_script"
  sudo env HYDRA_REF=dev bash "$upgrade_script"
)
```

Updater разрешает SHA ветки один раз и устанавливает именно этот commit, даже
если ветка сдвинется во время загрузки.

| Переменная | По умолчанию | Назначение |
| :--- | :--- | :--- |
| `HYDRA_REF` | `dev` | Ветка, чей точный SHA нужно установить |
| `HYDRA_REPO_URL` | официальный репозиторий | Git remote |
| `HYDRA_INSTALL_DIR` | `/opt/hydra` | Стабильная точка входа установки |
| `HYDRA_RELEASES_DIR` | `/opt/hydra-releases` | Каталог изолированных release |
| `HYDRA_UPGRADE_BACKUP_DIR` | `/var/backups/hydra/upgrades` | Постоянные снимки отката |

### Длительность простоя

Кратковременно останавливаются только службы и таймеры HYDRA. Sing-Box и внешние
прокси-бинарники updater напрямую не заменяет; длительность паузы в основном
определяется запуском ранее активных helper-служб.

Это возможно потому, что постоянные systemd units ссылаются на стабильный
`/opt/hydra` и интерпретатор `/opt/hydra/.venv/bin/python`, а не на физический
release-каталог: новый код и зависимости собираются до остановки процессов.

## Проверка результата

```bash
hydra check
hydra status
sudo systemctl --failed --no-pager
readlink -f /opt/hydra
```

Лог обновления — `/var/log/hydra/upgrade.log`. Каталог снимка печатается в
последней строке updater и содержит:

| Артефакт | Содержание |
| :--- | :--- |
| `metadata.env` | Исходный и целевой SHA |
| `state-before-upgrade/` | Сырой `/var/lib/hydra` до обновления |
| `hydra-backup.tar.gz` | Проверенный backup и результат его проверки |
| JSON-отчёты | Preflight, миграция state и post-cutover проверки |
| `active-units.txt` | Службы и таймеры, активные до обновления |
| `SUCCESS` | Маркер полного завершения |

> [!TIP]
> Не удаляйте последний снимок до того, как проверите реальный трафик,
> подписки и клиентские подключения.

## Если обновление завершилось ошибкой

Не запускайте поверх ошибки `bootstrap.sh` и не делайте `git reset --hard`.
Сначала соберите факты:

```bash
sudo tail -n 200 /var/log/hydra/upgrade.log
sudo systemctl --failed --no-pager
hydra check
```

Обычная ошибка приводит к автоматическому откату. В каталоге снимка при этом
остаются неудачный release, state после сбоя и исходный state.

Если автоматический откат не смог вернуть службу, восстанавливайте строго в этом
порядке:

1. остановить службы HYDRA;
2. вернуть `state-before-upgrade`;
3. вернуть прежний `/opt/hydra` и wrapper `hydra`;
4. выполнить `systemctl daemon-reload`;
5. запустить службы из `active-units.txt`.

Не удаляйте артефакты снимка до успешного восстановления.

## Схема state и миграции

В 2.5.4 актуальна схема **4**. Отдельно миграцию выполняет:

```bash
sudo hydra upgrade migrate-state
```

Команда предназначена для `upgrade.sh` и аварийных процедур. В обычной
эксплуатации вызывайте её только при остановленных процессах HYDRA и наличии
проверенного backup. Миграция идемпотентна: повторный вызов на актуальной схеме
не переписывает state.

Каждая ступень `vN → vN+1` — чистая функция, проверяемая отдельно; запись всей
цепочки выполняется атомарно. Неизвестная будущая версия схемы не считается
повреждением и не заменяется старым backup: загрузка завершается явной ошибкой
совместимости.

Инварианты state и правила конкурентности — в
[ARCHITECTURE.md](ARCHITECTURE.md#6-state-и-рабочее-состояние).
