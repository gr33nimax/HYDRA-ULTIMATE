# Режим нод Hydra — implementation plan

> Для агента-исполнителя: прочитать `AGENTS.md` и дизайн ниже целиком, выполнять задачи по порядку с red/green тестом на каждую; не запускать `bootstrap.sh`, `upgrade.sh`, `updater.sh` и uninstall локально. Это план, не разрешение на деплой.

**Цель:** одна ссылка подписки на основе выдаёт персональные профили основы и управляемых нод; ноды продолжают обслуживать клиентов без связи с основой.

**Дизайн:** `docs/superpowers/specs/2026-09-29-node-mode-design.md`.

**Стек:** Python 3.10–3.13; `ApplicationService`, `HostBackend`, `ConfigurationApplier`, плагины Hydra, stdlib TLS/HTTP, интерактивный OpenSSH для установки/удаления, systemd на целевом Linux. Новые сетевые зависимости добавлять только при доказанной необходимости.

**Главные инварианты:** `state.json` — только долговечная желаемая конфигурация; отдельный защищённый снимок подтверждённых профилей — для подписки; не писать state напрямую; все host-мутации через `HostBackend`, процессы через `hydra/utils/commands.py`; управление нодой только по аутентифицированному ограниченному API; без секрета в status/логе/argv; полная локальная работоспособность при потере связи; никаких дополнительных пользовательских состояний синхронизации.

**Review focus:** повтор после потери ответа на apply; AWG private keys при одинаковом пользователе на двух серверах; формат sing-box/HydraBox со совпадающими именами; перезапуск основы без связи с нодой; обрыв SSH при удалении.

## Техническое решение, которое нельзя «упростить»

1. Один управляющий сервер; каждая нода получает собственный `node_id`, самостоятельные ключи протоколов и локальный state. UUID пользователя общ для идентификации, но **не общий набор credential dictionaries**. Разрешённая проекция пользователя: UUID/email, blocked/expiry/limit/disabled_protocols и минимум нужных plugin-полей. Локальные генерируемые ключи ноды остаются на ней.
2. Нода экспортирует персональные структурированные клиентские материалы после успешного apply (для обычных ссылок и JSON-профилей). Основа не хранит «целую подписку ноды», не обращается к ноде из HTTP GET и не пересоздаёт её серверные ключи. Защищённый снимок на основе меняется атомарно после полного валидного экспорта; последний удачный переживает рестарт.
3. Изменение имени — локальная операция основы при выдаче: экспорт хранится без конечного имени или с отдельным его исходным полем. Ключ переименования `(node_id, protocol, profile)`; существующие имена основы и личные имена сохраняют своё значение. Новую ревизию/sequence подписки формировать при реальном изменении опубликованного состава/имени.
4. При включении/выключении протокола основа показывает успех лишь после подтверждённого apply и обновлённого экспорта. При недоступной ноде этот пункт заблокирован. Изменения пользователей на основе сохраняются и сверяются после возвращения связи; нода не знает о новой блокировке до этого момента. Сами пользовательские лимиты в офлайне работают по последним полученным данным.
5. Общий трафик: монотонный вклад каждой ноды, агрегированный на основе; эпоха сброса отделяет новый период от старых отчётов. Без связи строгий общий лимит недостижим; UI/документация не обещают его.

Отдельно отметить custom Throne/NekoBox и AWG. Не показывать в мастере протокол, который невозможно выдать ни в одном поддерживаемом формате; несовместимый формат не должен молча давать неверный профиль.

**Гейт:** контракт принимает реальные профили плагинов, AWG-ключи двух нод независимы; границы архитектуры не изменены ради обхода тестов.

### 2. Persisted model и миграция

**Править:** `hydra/core/state_nodes.py` (новый), `hydra/core/state_models.py`, `hydra/core/state_format.py`, `hydra/core/state_validation.py`, `tests/test_state*.py`, `tests/test_node_state.py`.

- [ ] **Решение: `STATE_FORMAT_VERSION` не повышается.** Пространство имён `nodes` добавляется в `_FEATURE_KEYS` и получает значение по умолчанию, поэтому старый документ читается без миграции, а старый runtime сохраняет неизвестное пространство имён в `feature_extensions` и не теряет его. Повышение версии сломало бы возможность отката на прежний runtime без восстановления state. ## Порядок ревью и стоп-условия

Сначала 1–2 (контракты/state), затем 3–5 (runtime и безопасный канал), затем 6–8 (экспорт/форматы/трафик), затем 9 (TUI/установка/удаление/документы). Не параллелить изменения общего state schema и подписочных генераторов без согласованного контракта экспорта. На каждом этапе сначала тест, затем минимальный код, затем целевая проверка. Не объявлять feature готовой, пока нет успешного end-to-end Linux smoke, подтверждения всех форматов подписок и удаления без затрагивания чужих ресурсов.
