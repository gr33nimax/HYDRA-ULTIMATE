# TUI экраны режима нод: план

Цель: оператор без знания внутренностей отвечает на три вопроса — **работает ли нода**, **попали ли её профили в подписки**, **что именно сломано и что нажать**. На самой ноде — **что применено, что не работает, когда была последняя команда основы**.

Опирается на уже существующее: `hydra/ui/tui.py` (`panel`, `kv`, `menu`, `prompt`, цвета, ширина 78), рантайм-наблюдения `hydra/services/nodes/observation.py`, публикацию и покрытие из основы. Никаких новых зависимостей и никакой второй модели состояния: экраны читают то, что уже пишется.

## 1. Принципы

1. **Один экран — один вопрос.** Список отвечает «что с моими серверами», карточка — «что с этой нодой и что делать».
2. **Состояние словами.** `generation`, `digest`, `SHA`, `contract` живут только в «Подробностях». В обычном экране — «опубликовано 6 профилей», «применение не завершено».
3. **Ошибка = этап + причина + действие.** «Применение настроек: AnyTLS не подготовлен → [1] Исправить настройки». Никаких `RuntimeError` и кодов вроде `apply_failed`.
4. **Одно главное действие.** Клавиша `1` всегда делает то, что нужно сейчас; остальное — вторично. Набор пунктов зависит от состояния, а не от внутреннего списка операций.
5. **Свежесть вместо «не проверена».** «проверка 12 с назад», «проверка 6 мин назад (устарела)».
6. **Нет данных — «неизвестно».** Никогда не выдавать «работает» за отсутствие наблюдения.
7. **Ничего лишнего.** VK cookies — только у ноды с Calls; удаление и отсоединение — в «Опасных действиях»; офлайн-операции помечены явно.

## 2. Словарь состояний (ядро плана)

Одна чистая функция превращает наблюдение и запись ноды в состояние. Экран только печатает результат.

| Состояние | Слово в интерфейсе | Цвет | Главное действие |
|---|---|---|---|
| `unknown` | не проверялась | DIM | Проверить связь |
| `connecting` | проверяем… | CYAN | — |
| `offline` | нет связи · используются последние профили | RED | Проверить связь |
| `needs_setup` | нужна настройка: <причина> | YELLOW | Исправить настройки |
| `applying` | применяются изменения | CYAN | — |
| `partial` | работает частично · <протоколы без профилей> | YELLOW | Протоколы и профили |
| `ready` | работает · N профилей | GREEN | — |
| `update_pending` | обновление: ожидает перезапуска | CYAN | Обновление программы |
| `update_complete` | обновление выполнено | GREEN | — |
| `storage_broken` | публикация повреждена | RED | Опубликовать заново |

Правила вывода состояния (порядок проверок, первое совпадение):

1. нет наблюдения → `unknown`;
2. `control == error` и `stage == connect` → `offline`;
3. `stage == apply` и есть `message` → `needs_setup`;
4. `published_generation <= 0` → `needs_setup` (причина: «профили не опубликованы»);
5. есть предупреждения о протоколах без профилей → `partial`;
6. `upgrade == pending` → `update_pending`;
7. иначе → `ready`.

Отдельно от состояния — три независимые строки, которые не смешиваются: **Связь** (доступность + свежесть), **Подписки** (покрытие по протоколам), **Обновление** (цель/установлено).

## 3. Экраны основы

### S1 «Серверы»

```text
  НОДЫ
  ╭────────────────────────────────────────────────────────────────────────╮
  │  [1]  Добавить сервер                                                  │
  │       SSH + mTLS, 4 шага                                               │
  │  [2]  Великобритания · UK                    работает · 6 профилей     │
  │       проверка 12 с назад                                              │
  │  [3]  Финляндия                              нет связи · последние      │
  │       профили; проверка 6 мин назад (устарела)                         │
  │  [0]  Назад                                                            │
  ╰────────────────────────────────────────────────────────────────────────╯
```

Требования: одна строка состояния на нод; «сколько профилей» — из покрытия; «когда проверялась» — из наблюдения; при отсутствии наблюдения — «не проверялась», без красного.

### S2 «Нода»

```text
  НОДА · Великобритания
  ╭────────────────────────────────────────────────────────────────────────╮
  │  Состояние        нужна настройка: применение не завершено             │
  │  Связь            доступна · проверка 12 с назад                       │
  │  Подписки         0 профилей · amneziawg, anytls, vless                │
  │  Обновление       выполнено · установлено 4973ca3 (цель 4973ca3)       │
  │  Причина          применение настроек: AnyTLS не подготовлен            │
  ╰────────────────────────────────────────────────────────────────────────╯

  ЧТО ДЕЛАТЬ
  ╭────────────────────────────────────────────────────────────────────────╮
  │  [1]  Исправить настройки                                              │
  │  [2]  Проверить связь                                                  │
  │  [3]  Протоколы и профили                                              │
  │  [4]  Обновление программы                                             │
  │  [5]  Подробности                                                      │
  │  [6]  Опасные действия                                                 │
  │  [0]  Назад                                                            │
  ╰────────────────────────────────────────────────────────────────────────╯
```

Требования: «Причина» появляется только когда она есть; текст причины обрезается по ширине панели; набор пунктов строится по состоянию (для `ready` первый пункт — «Проверить связь», для `offline` — «Проверить связь», для `needs_setup` — «Исправить настройки»); «Опасные действия» присутствуют всегда, но последними.

### S3 «Протоколы и профили»

```text
  ПРОТОКОЛЫ · Великобритания
  ╭────────────────────────────────────────────────────────────────────────╮
  │  [1]  AmneziaWG 3.1          включён · 10 профилей                     │
  │  [2]  AnyTLS                  включён · профили не готовы              │
  │  [3]  VLESS (Reality)         включён · 10 профилей                    │
  │  [4]  Добавить протокол                                                │
  │  [0]  Назад                                                            │
  ╰────────────────────────────────────────────────────────────────────────╯
```

«N профилей» — из покрытия опубликованного снимка; «профили не готовы» — протокол включён, но покрытия нет. Вход в протокол открывает только его параметры (условные поля уже реализованы), а не общий JSON.

### S4 «Подробности»

Служебные факты, нужные при разборе: контракт, применённое и опубликованное поколение, digest, цель и установленная ревизия, время последней проверки и последнего успеха, этап и код последней ошибки, таблица покрытия, последние строки журнала применения. Ничего из этого не показывается на S1/S2.

### S5 «Опасные действия»

Без изменений по смыслу: отсоединение (VPS продолжит работать) и удаление (очистка по SSH) с подтверждением точного имени. Оба — только отсюда.

## 4. Экраны ноды

### N1 «Нода uk-1» (аварийный доступ, только чтение)

```text
  НОДА · uk-1 · управляется основой
  ╭────────────────────────────────────────────────────────────────────────╮
  │  Основа           https://sub.gr33nimax.ru                             │
  │  Ядро             запущено · sing-box 1.14.1                           │
  │  AmneziaWG        работает · 10 профилей                               │
  │  AnyTLS           работает · 10 профилей                               │
  │  VLESS (Reality)  работает · 10 профилей                               │
  │  Последнее применение  не выполнено · этап «протоколы» · 21:16         │
  │  Причина          AnyTLS inbound is missing from the applied config     │
  │  Пользователи     11 · блокирован 1                                    │
  │  Ревизия          4973ca3                                              │
  ╰────────────────────────────────────────────────────────────────────────╯
```

Требования: имена протоколов — через общий `protocol_label` (никогда не пустые); «N профилей» — по локальному состоянию; «Последнее применение» — из журнала применения с временем; «Причина» — только при наличии. Никаких «: работает» с пустым именем.

### N2 «Подробности и журнал»

Полная ошибка, контракт, ревизия, слушающие порты и юниты, хвост журнала применения. Действия: «Обновить сведения», «Назад».

## 5. Куда это ложится в коде

| Файл | Что | Почему так |
|---|---|---|
| `hydra/ui/_menus/node_status.py` (новый) | словарь состояний: `state_of(node, observation) -> NodeStatus` + строки «Связь», «Подписки», «Обновление», «Причина» | одна чистая функция, тестируется без терминала, используется и основой, и нодой |
| `hydra/ui/_menus/nodes.py` | S1, S2, S3, S5 | уже владелец этих экранов; держать ≤ 500 строк |
| `hydra/ui/_menus/node_details.py` (новый) | S4 | не раздувать `nodes.py` |
| `hydra/ui/_menus/node_emergency.py` | N1, N2 | экран ноды остаётся read-only |
| `hydra/ui/_menus/nodes_setup.py` | финальный экран установки: план + «что дальше» | мастер уже собирает план |
| `hydra/services/nodes/observation.py` | без изменений | состояние выводится в UI, сервис остаётся про факты |

Сервисный слой не меняется: экраны не делают выводов, которых нет в наблюдении и состоянии. Если для состояния не хватает факта (например, «применяются изменения»), это отдельная правка наблюдений, а не выдумка в интерфейсе.

## 6. Тесты и приёмка

Обязательные тесты:

1. **Таблица состояний**: для каждого состояния из §2 — свой набор фактов на входе и ожидаемые слово, цвет и главное действие. Это и есть контракт экранов.
2. **Рендер**: панели не выходят за ширину при 80 и 60 колонках; длинная причина обрезается; пустые имена протоколов подменяются на `protocol_label`.
3. **Навигация**: `0` — назад без обращений к сервисам; главное действие вызывает ровно один метод; опасные действия требуют точного имени.
4. **Нода**: экран не меняет state и host (существующий guard расширяется на новые пункты).
5. **Предпросмотр**: расширить `.pi/render-tui-preview.py` — рендер всех состояний в текстовый файл, чтобы экраны можно было посмотреть без VPS.

Приёмка: оператор, открыв S1 и S2, отвечает на три вопроса из шапки плана, не заходя в «Подробности»; на N1 видит, что применено, что не работает и когда была последняя команда основы.

## 7. Порядок работ

- **P1**: `node_status.py` + S1 + S2 + N1 (закрывает жалобы «сырое», «health check», «непонятно, что делать»).
- **P2**: S3 + S4 + S5 + N2 (разгружает карточку, убирает служебные пункты).
- **P3**: финальный экран установки, предпросмотр всех состояний, обновление `docs/NODES.md`.

Каждая часть — отдельный коммит с тестами из §6 и прогоном полного `verify.py`.
