# Режим «основа ↔ нода»: технический дизайн

Статус: проект для согласования; реализация не начата.

## 1. Цель и границы

Один установленный сервер Hydra («основа») владеет пользователями и единственным публичным сервером подписок. Из пункта `9 Ноды` основа устанавливает и управляет другими VPS. Нода запускает только нужные ей протоколы и их зависимости, не запускает Telegram-бота и публичный сервер подписок. Нода обслуживает клиентов с последней успешно применённой конфигурацией даже без связи с основой. Меню на самой ноде ограничено чтением статуса/ошибок и аварийным откатом. На основе и на разных нодах протоколы могут различаться.

Только функции Hydra и принадлежащие ей файлы/службы; никаких произвольных команд и администрирования чужих служб VPS через управление нодой. Имена профилей ноды независимы от одноимённых профилей основы/других нод. Своя ссылка подписки у пользователя не меняется.

Не добавлять пользовательские «этапы синхронизации» и очередь команд в TUI: показывать лишь доступность, последнюю проверку и ошибку. Технический номер поколения/ревизии для идемпотентности не является отдельным пользовательским состоянием.

## 2. Владение данными

| Данные | Владелец | На ноде |
|---|---|---|
| Пользователь: стабильный ID/UUID, email, блокировка, срок, лимит, индивидуальный запрет протокола | основа | локальная проекция только нужных полей |
| Протоколы, их параметры, регион, отображаемое имя и ветка конкретной ноды | основа | последняя применённая конфигурация протоколов |
| Выданные конкретной нодой ключи пользователей и её серверные ключи | нода | хранятся локально; на основу идут только клиентские артефакты, необходимые для подписки |
| Счётчики трафика конкретной ноды | нода | отчёт об абсолютных счётчиках на основу; основа считает агрегат без двойного счёта |
| Подтверждённый экспорт клиентских конфигов по пользователям, без финальных подписочных названий | нода | основа хранит защищённый последний удачный снимок отдельно от desired `state.json`; имена применяет при выдаче |
| Действительность URL подписки и лимит устройств при запросе | основа | не проверяется собственным сервером подписок |

Нельзя копировать `AppState` основы целиком: там есть секреты Telegram/подписок, runtime-счётчики и данные плагинов, которые на ноде не нужны. Нельзя перезаписывать весь `User.credentials` с основы: у AWG ключи генерируются отдельно, повторное использование на нескольких серверах не должно перетирать профиль другого сервера. Не копировать сертификаты основы на ноду: домены ноды и TLS/ACME настраиваются там через существующие владельцы протоколов.

На основе добавить долговечный описатель ноды в `AppState` (id, имя, регион, адрес управления, выбранная ветка/версия, настройки выбранных плагинов и подписи). Добавление пространства имён `nodes` — аддитивное изменение: документ старого формата читается без миграции, а прежний runtime сохраняет неизвестное пространство имён в `feature_extensions`, поэтому откат возможен без восстановления state. Несовместимая (не аддитивная) смена формы узлов требует отдельного повышения `STATE_FORMAT_VERSION` на +1 с цепочкой миграций, fixture старой схемы и проверкой совместимости `upgrade.sh`. Не хранить SSH-пароль и приватные ключи управления в публичном status или в state. Последний подтверждённый экспорт — отдельный atomic/0600 файл с ограничениями размера и проверкой содержимого; он восстанавливается после перезапуска основы, не превращается в desired state. На ноде хранится собственный локальный `AppState` для последних применённых протоколов и пользователей.

## 3. Сеть и безопасность

- Первая установка и окончательная очистка — интерактивный SSH. Ввод пароля замаскирован; пароль не записывается в Hydra/логи и не передаётся аргументом процесса. Проверять host key (TOFU с явным отпечатком/подтверждением либо заранее доверенный ключ), не использовать `StrictHostKeyChecking=no`. Перед root-операцией показать точную цель и запросить подтверждение.
- Обычное управление — ограниченный HTTPS API ноды на выделенном TCP-порту; вход на этот порт разрешён только с IP основы, плюс обязательная взаимная аутентификация TLS с отдельными удостоверениями каждой ноды. Фильтр по IP — дополнительная защита, не замена идентификации. Отдельная ротация/отзыв удостоверений; не использовать публичный токен подписки для администрирования.
- API не принимает shell, имя произвольного файла или путь для чтения/удаления. Только версии протокола, проверка, применение типизированной проекции, экспорт клиентских профилей, агрегированные счётчики, безопасные диагностические сведения и штатное обновление. Ограничение тела, времени, частоты, защита от повторного применения устаревшей ревизии.
- Если IP основы поменялся и управление недоступно, вход по SSH на ноду с явным подтверждением корректирует firewall и обновляет доверие. Никогда не оставлять API открытым всему интернету «на время настройки».
- Таймауты всех сетевых действий, отсутствие команд с секретами в argv/логах, redaction ошибок, без вывода ссылок/ключей в общей диагностике. Производственные привилегированные операции через injected `HostBackend`, запуск процессов только через `hydra/utils/commands.py`.

## 4. Установка, применение, повторное подключение

1. Основа проверяет готовность HTTPS-сервера подписок, SSH, ОС/Python, отсутствие чужой Hydra или предлагает явно отдельный сценарий для уже установленной; уникальность ID/IP, DNS/TLS и занятость портов выбранных протоколов. Показывает план до мутаций.
2. По SSH запускается только проверенная версия установки Hydra с зафиксированной веткой и commit SHA (режим `node`). Существующий `bootstrap.sh` на чистой установке создаёт `default`-пользователя: в режиме ноды это должно быть отключено. Нельзя запускать локально `bootstrap.sh`/`upgrade.sh`; их меняют и проверяют статически, Linux smoke — в CI/изолированной VPS.
3. Режим `node` фиксируется при установке, запускает управление и нужные runtime-службы без сервера подписок/Telegram/главного TUI. Устанавливаются взаимное доверие API и ограничение firewall. Для запрошенного протокола проверяется совместимость версии ноды/основы.
4. Основа посылает ноде **полный актуальный снимок для этой ноды**: проекцию пользователей и выбранные настройки. Нода сверяет ревизию, сохраняет свою локальную прошлую рабочую конфигурацию, через доменные сервисы/`ConfigurationApplier` проверяет и применяет изменения, делает health-check. При ошибке откатывает локальный state и runtime. Не подменять это прямой записью `state.json` или вызовом отдельных plugin lifecycle из UI.
5. После подтверждения нода экспортирует для каждого применённого пользователя только его клиентские материалы для форматов подписки. Основа проверяет идентификатор ноды, ревизию, полноту пользователей, структуру и размер. Изменения настроек протокола на основе сначала готовятся в памяти: после успешного apply и проверки экспорта записать неизменяемый снимок нового поколения в защищённый файл, затем атомарно сохранить desired state с указателем на опубликованное поколение. GET подписки читает только поколение, на которое указывает state; старый файл сохраняется до успешного переключения. Указатель означает выбранную для публикации желаемую конфигурацию, а не runtime-health. Если сохранение state не удалось, старый указатель и старый снимок остаются опубликованными, новый файл можно удалить/повторить; повторная сверка возвращает ноду к актуальному desired state. При перезапуске файлы без опубликованного указателя игнорируются. Нельзя выдавать новый профиль раньше фактического применения на ноде.
6. Основа повторяет сверку при появлении связи и после локальных изменений пользователей/протоколов; команда «проверить связь» — read-only. Если нода отключена, она сохраняет последний применённый state, а основа — последний подтверждённый экспорт. После восстановления отправляется текущий полный снимок, а не длинная очередь событий.

Никакой общей атомарной транзакции на два VPS нет. При отказе после применения на ноде, но до подтверждения/фиксации экспорта на основе повторно отправить тот же снимок идемпотентно либо восстановить прежний desired state на ноде; не показывать успех раньше подтверждения. Сбои между записью нового файла и переключением указателя должны быть разрешимы после рестарта: GET продолжает использовать старое поколение, новый файл без указателя игнорируется. Если указатель уже сохранён, соответствующий снимок обязан существовать и проходить проверку хэша/схемы; старые файлы очищаются только после этого. Изменения пользователя на основе сохраняются даже при недоступности ноды; это eventual consistency, а не ложная гарантия мгновенной блокировки.

## 5. Как строится подписка

`/sub/<UUID>` и проверка пользователя/лимита устройств остаются на основе (`hydra/services/subscriptions/server.py`). Генератор для пользователя получает собственные профили основы и последний подтверждённый экспорт **только для этого же UUID** от всех добавленных нод. Активный протокол ноды публикуется после успешного применения и экспорта; выключенный удаляется после успешного применения; при обычной потере связи старые профили остаются. Только явная успешная очистка удаляет ноду и её экспорт.

Экспорт не равен готовой удалённой подписке: это структурированные персональные клиентские профили без окончательного имени; при выдаче основа применяет текущее имя, в том числе изменённое во время недоступности ноды. Адаптировать все варианты: base64, Shadowrocket, NekoBox, Throne, sing-box JSON и HydraBox/JWE. В JSON объединять outbounds/endpoints и связи между ними без конфликтов тегов; в HydraBox ресурс/профиль ID должны включать стабильный node ID, а sequence возрастать при смене опубликованного содержимого. Название профиля привязывается к `(node_id, protocol, profile)`; приоритет: личное имя пользователя для этой ноды → общее имя профиля этой ноды → стандартное имя с регионом. Старые несвязанные имена основы не перезаписываются; личные overrides пользователя получают namespaced ключи ноды без повторного использования существующих ключей основы. Токен/UUID подписки, сертификат/домен подписок и клиентские URL основы не меняются.

Для нового пользователя, добавленного при отключённой ноде, нодных профилей нет до первого успешного применения. Старые пользователи сохраняют последние подтверждённые профили. Если пользователь заблокирован на основе, URL прекращает выдачу, но при разрыве всех каналов он может продолжать пользоваться нодой со старым доступом до синхронизации; это выбранная политика offline continuity.

## 6. Трафик, срок действия, лимиты

Лимит/блокировка/индивидуальные отключения передаются ноде и применяются её существующими сервисами. Нода должна самостоятельно проверять известный ей срок действия пользователя в офлайне; обновлённый на основе запрет офлайн неизвестен. Трафик ноды приходит абсолютными per-user счётчиками с идентификатором ноды и эпохой сброса, чтобы повторы и рестарты не удваивали сумму; основа агрегирует local + nodes для `Subscription-Userinfo`, UI и блокировки при лимите. Сброс трафика требует согласованной новой эпохи; старые отчёты после сброса игнорируются. Лимит устройств, измеряемый при запросе подписки, остаётся проверкой на основе; существующие механизмы ограничения реальных одновременных подключений проверять отдельно на совместимость с несколькими VPS.

Без связи нельзя гарантировать мгновенный общий трафик-лимит на нескольких серверах; по умолчанию итоговые лимиты **best-effort** после сверки, и превышение в офлайне возможно. Не заявлять строгий распределённый лимит или мгновенную блокировку. Не запускать фичу с лозунгом «общие лимиты гарантированы в реальном времени».

## 7. TUI (только через `ApplicationService`)

`9 Ноды`: список (имя, регион, IP, связь) → установка или карточка. Мастер: SSH-доступ → имя/регион/ветка (авто = ветка основы на момент установки) → выбор протоколов → существующие настройки каждого протокола (домены/IP клиентского подключения вводятся внутри них, не в общем поле) → видимые имена → проверка/подтверждение. Карточка: протоколы/изменить или включить-выключить; названия профилей ноды; сведения (версия, адрес, последняя проверка); диагностика/обновление; очистка. Скрытого «опубликовать» нет: успешно включённый subscription-capable профиль публикуется автоматически. При отключённой связи менять протоколы нельзя, названия на основе менять можно. Просмотр не мутирует host/state. Ввод опасных операций с предварительным планом и подтверждением.

В TUI самой ноды лишь статус, последние ошибки и аварийный возврат последней рабочей конфигурации; без обычных пользователей, настроек протоколов и подписок. Точный текст/карта экранов берутся из согласованного диалога, но подписи должны быть однозначны и тестируемы.

## 8. Очистка и обновление

Удаление: показать `uninstall_plan`, повторно получить SSH-доступ, проверить host fingerprint и идентичность управляемой установки, потребовать ввод имени ноды, применить существующий `UninstallService` с `keep_data=False` только к Hydra-owned ресурсам. После подтверждённого удаления/проверки удалить на основе запись и экспорт. При обрыве после возможной очистки не заявлять успех: повторная проверка по SSH различает «уже удалено» и «ещё установлено»; повтор безопасен. Если нода недоступна, удаление не делается и её конфиги остаются; нет операции «забыть, не очистив VPS» в первой версии. Снимать правила firewall только те, что принадлежат Hydra; чужие правила/пакеты не удалять.

Обновление ноды — штатный `upgrade.sh` с snapshot и rollback на самой ноде, проверка совместимости control API/схемы перед обновлением; нельзя обновлять ноду до несовместимой с основой версии. После успешного обновления — сверка и повторный экспорт. Смена ветки не является тихим `git checkout` из меню.

## 9. Приёмка и обязательные отказы

- Добавление двух нод с одинаковым протоколом и одного пользователя даёт два независимо названных профиля плюс профиль основы; формат, содержащий JSON, и HydraBox также работают.
- Создание/удаление/блокировка пользователя, смена срока, личный запрет протокола, ротация ключей/профилей и трафик корректно доходят до включённых протоколов ноды без повторного использования локальных ключей другой ноды.
- Прерванная связь оставляет ноду обслуживать старых пользователей и сохраняет их ссылки; новый пользователь не получает несозданный нодный профиль; после восстановления актуальное состояние сходится без повторных ключей/профилей/счётчиков.
- Неверная авторизация, чужой IP, повтор старой ревизии, слишком большой/подменённый экспорт, TLS-ошибка, обрыв на каждой границе установки/apply/экспорта/удаления не изменяют подтверждённую подписку и не открывают host-доступ.
- `plan`, `status`, `doctor`, `dry-run` не меняют state и хост; атомарная запись/revision, rollback/journal и архитектурные guard'ы проходят.
- Python 3.10–3.13 unit; отдельные Linux integration smoke на изолированной VPS/root для firewall, systemd, SSH, TLS, bootstrap, upgrade и uninstall; Windows unit не подменяют эту проверку.
