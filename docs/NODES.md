# Managed nodes v2

HYDRA управляет удалёнными серверами через `ApplicationService.nodes` и namespace
`feature_extensions.managed_nodes`. Текущая модель не использует `AppState.nodes`
или старый mTLS control protocol. Старые node-only API, entrypoints и subsystem
удалены по контракту владельца; старые node records не импортируются и не становятся
новыми definitions. Неизвестные поля state сохраняются общим механизмом round-trip,
но HYDRA их не интерпретирует и не публикует.

## Enrollment и transport

TUI открывается пунктом `9 Ноды`. Мастер запрашивает идентификатор, имя, IP-адрес,
SSH-учётную запись, SSH-порт, параметры протокола и ветку исходного кода. SSH host
key показывается до подтверждения; source branch разрешается в точный commit SHA и
фиксируется в плане установки. Пароль SSH передаётся через одноразовый канал и не
попадает в persisted operation. Установка, удаление и управление credentials идут
через application service и injected SSH/backend owners. После выхода из мастера
экран с результатом или ошибкой остаётся до Enter; меню не очищает его сразу.

Удаление доступно и после незавершённой установки: используется её сохранённый
план с закреплённой SSH identity. Подтверждённое удаление атомарно заменяет
незавершённые install/apply операции; их больше нельзя возобновить. Запись ноды
и credentials сохраняются до подтверждения очистки VPS по SSH. Если установка
не успела создать ресурсы, чистое состояние VPS подтверждается без запуска
отсутствующего uninstall. Повторный выбор «Удалить ноду» продолжает сохранённую
операцию удаления, включая локальную очистку после успешного remote uninstall.
Основа запускает штатный CLI uninstall напрямую из `/opt/hydra`, с root и
`--yes`: старый `main.py` ноды с запретом команд не блокирует удаление. Для этой
совместимости достаточно обновить основу; обновление удаляемой ноды не требуется.

Карточка показывает строки состояния и отдельные результаты диагностики, включая
причины ошибок и ID операций. Незавершённую установку можно продолжить через
пункт `5`: используется сохранённый план и тот же operation ID. На этапе apply
синхронизация сохраняет этот ID при ожидании ответа ноды; для старых записей с
утраченным маркером этапа восстановление допускается только после подтверждённого
enrollment и при наличии сохранённого неизменяемого apply intent.

При применении AmneziaWG на новой ноде application preflight создаёт локальный
профиль и ключи до рендеринга конфигурации. Повторное применение сохраняет ключи.
Для этого исправления обновлять нужно и основу, и установленную ноду.

Рабочая management surface — ограниченный mTLS `/v1` agent с закреплённой identity
ноды. Она предоставляет состояние, durable operation lookup, apply и подтверждённые
профили; это не публичная административная панель. Дополнительные typed cascade endpoints
`/v1/cascades/{snapshot,prepare,material,status,apply,rollback,finalize}` принимают только
operation/plan/route/protocol/receiver-bound DTO. Server принимает только закреплённую base
client identity; receiver ID берётся из локального protected identity, не из запроса. Route
seed и transit outbound передаются только по этому каналу и сохраняются как protected
operation-scoped material; произвольные config/path/command RPC не предоставляются.
Локальная роль ноды определяется маркером `/etc/hydra/managed-node/identity.json`; роль
открывает только аварийную read-only диагностику и ограниченный CLI.

## Apply, recovery и sync

Изменение протокола сначала выполняет один state update/CAS, который записывает
новую `NodeDefinition`, неизменяемый `NodeDesired` в frozen operation plan и pending
operation. Только после commit вызывается sync и начинаются сетевые действия. Если
CAS конфликтует или падает, ни новое определение, ни операция не видны. Если процесс
падает после commit, тот же operation ID и payload восстанавливаются из persisted
state; неизвестный результат отправки сверяется через operation endpoint и не
переигрывается вслепую.

После отправки основа ожидает итог этой же операции до 60 секунд, опрашивая её статус
с интервалом 0,5 секунды. Отдельный запрос ограничен 10 секундами и оставшимся общим
временем. Каждый ответ повторно проверяется на соответствие ID ноды, операции и
digest неизменяемого задания. Успех показывается только после получения ApplyReceipt,
проверки активного runtime и сохранения подтверждённых профилей на основе.
При потерянном ответе на отправку продолжается только опрос того же ID. При таймауте
операция остаётся незавершённой; меню сообщает об отсутствии подтверждения, а обычная
автоматическая синхронизация проверяет результат позже без нового задания.

Node-side apply сохраняет snapshot до host effects, подтверждает runtime и локально
сохранённые profile bundles до выдачи `ApplyReceipt`; при ошибке использует rollback
и durable recovery state. Обычный Sync Agent использует тот же per-node coordinator
раз в пять минут. Синхронизация конкретного node ID не запускает base-wide maintenance.
Обычный production apply сверяет актуальные persisted cascade-операции до preflight и
держит локального base/node participant вне изменений до освобождения lease; отдельный
participant apply идёт через canonical configuration owner и sealed operation-bound
авторизацию. Participant snapshots и transaction receipts защищены checksummed storage и
остаются до подтверждённого rollback/finalize; неизвестный результат не переигрывается.

Apply proof и учёт трафика используют разные идентификаторы:

- `apply_generation` привязан к process identity и digest наблюдаемой runtime-конфигурации.
  Изменение config инвалидирует старый receipt, даже если PID не изменился.
- `runtime_id` отражает только epoch работающего процесса и служит billing baseline.
  Поэтому config-only change с теми же absolute counters не создаёт повторное списание;
  перезапуск и явный reset сохраняют отдельную учётную семантику.

Управление квотами остаётся ограничено доступностью и достоверностью данных самого
транспорта; строгая мгновенная глобальная квота при разрыве связи не обещается.

## Subscriptions и checks

`ConfirmedProfiles` читаются локально, сверяются с успешной operation receipt и
пользовательской identity. Обычный GET подписки не открывает сетевое соединение к
удалённой ноде. Main users, их локальные профили и URL подписок продолжают идти через
существующие subscription owners; credentials ноды не выдаются в статусе или логах.

Diagnostics разделяют management response, runtime/apply proof, user coverage,
subscription bundle и transport checks. Отсутствующая возможность показывает
`unknown`/`not_applicable`, а не simulated success.

Для AmneziaWG без native-client probe карточка показывает подтверждение
конфигурации с подписью «(конфигурация)»; это не подтверждение клиентского handshake.
В обычной подписке `wg://` и `vpn://` одного AWG-профиля не дублируются: используется
`wg://`, а `vpn://` остаётся запасным вариантом и отдельным ручным импортом.
Название Amnezia записывается внутрь контейнера, а не только в URI fragment.
Desktop и Mobile экспортируются отдельными sing-box документами.

Настройки протокола открываются через `Протоколы → выбранный протокол`. Здесь
можно изменить параметры, переименовать конфигурации этого протокола или удалить
его с ноды. Открытие параметров без изменений не вызывает подтверждение и apply;
сравнение учитывает значения по умолчанию и параметры, зависящие от режима.
Удаление сохраняет оставшиеся протоколы и pending apply одним state update, затем
отключает протокол на ноде и получает обновлённые профили. Можно удалить последний
протокол, сохранив управление нодой. При сбое намерение сохраняется для повторной
синхронизации; результат не выдаётся за успешное удаление. Нельзя менять протоколы
ноды, пока она участвует в каскаде или выполняет другую операцию.

Пункт `Название конфигурации` в настройках протокола меняет общие имена его
опубликованных профилей. Эти же профили доступны в редакторе личных имён пользователя. Общие и
личные имена используют стабильный ключ ноды/протокола/варианта; личное имя имеет
приоритет, пустое значение сбрасывает override. Правка имени не требует remote apply.
Флаг стандартного имени берётся из кешированной геолокации IP ноды, которую
обновляет sync; GET подписки не делает сетевых запросов для геолокации. Если данных
нет, показывается 🌐. В собственное имя можно включить нужный флаг вручную.

## Каскады VLESS / AnyTLS

В меню `Ноды → Каскады` выбираются разные входной и выходной участники: основа и
нода в любом направлении либо две ноды. Для каждого выбранного протокола оба
участника должны иметь настроенный совместимый транспорт. Обычные подключения
пользователей сохраняются: отдельный scoped auth-user направляется на второй
сервер, а транзитный контекст выходит напрямую. При недоступном втором сервере
входной контекст не переключается на прямой выход.

Нужны обновлённые основа и обе ноды, а также HydraCore с `with_v2ray_api`.
Возможности не объявляются по названию версии: установленный исполняемый файл
проходит изолированную проверку аутентифицированной маршрутизации и накопительных
счётчиков для каждого протокола. Сборка без API или неподдерживаемая конфигурация
не получает доступного пункта протокола. Самопроверка не меняет systemd, firewall,
пользователей и рабочую конфигурацию.

Перед активацией сохраняются снимки обоих участников и неизменяемое задание.
Подготовка передаёт scoped credentials только по закреплённому mTLS-каналу.
Учётные данные AnyTLS для этих временных контекстов переносимы между участниками
и выводятся из случайного защищённого route seed; обычные credentials AnyTLS и
ключ каждой установки не меняются.

После подтверждённого применения запускается настоящий клиент только с входной
конфигурацией. Проверка требует успешного HTTPS-ответа и прироста отдельного
технического счётчика на выходе при неизменном process/config proof. Открытые порты
или две независимые прямые проверки не считаются доказательством каскада.
API счётчиков слушает только `127.0.0.1:19091` и включается при наличии scoped
контекстов, а не во всех установках.

Профили каскада хранятся отдельно от обычных node bundles. Публикуется только
входной credential пользователя; транзитный credential и технический probe не
попадают в подписки. До durable coordinator commit читатель использует предыдущий
подтверждённый bundle. Переименование меняет подпись без rekey/apply. Чтение подписки
локальное и фильтрует текущие блокировки, срок действия и отключённые протоколы.

Квота списывается только за business entry context. Транзит и probe не списываются;
обычные подключения на выходном сервере учитываются как раньше. Финальный sample
снимается до удаления контекста и сохраняется после удаления. Counter reset,
перезапуск процесса и пользовательский reset имеют отдельные baseline/epoch.

Существующий targeted/five-minute sync доставляет актуальных пользователей и
контексты и повторяет path proof/publication. Если подтверждение пути потеряно,
профили каскада скрываются до успешной проверки. Неопределённая операция сохраняет
leases и снимки; её можно продолжить пунктом «Восстановить каскад». Потерянный
ответ apply сверяется с точным runtime/target proof до повтора. Удаление каскада
очищает всех участников до освобождения credentials; недоступный участник не
считается очищенным.

Изолированный Linux data-plane стенд запускается отдельно:
`HYDRA_CASCADE_CORE=/absolute/path/sing-box python -m pytest -v tests/test_cascade_live.py`.
Он использует реальные процессы ядра, VLESS/XHTTP, AnyTLS, gRPC и pinned mTLS,
проверяет все три топологии, выдачу профиля, entry-only billing и отказ без fallback
после остановки выхода. Он не запускает установщик, systemd или firewall. Отдельный
workflow `Cascade real-engine acceptance` собирает ядро из закреплённого source SHA.
Эти проверки не заменяют canary на реальных VPS и проверку клиентских приложений.
