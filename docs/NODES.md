# Основа и управляемые ноды

Основа хранит желаемую конфигурацию пользователей и нод. Нода обслуживает клиентов
самостоятельно: серверные ключи, credentials протоколов и runtime-счётчики создаются
и остаются на ней. Общий UUID пользователя служит идентификатором, а не набором
общих секретов.

## Меню основы

Пункт `9 Ноды` открывает список и карточку. Список ничего не опрашивает: он читает
последнее наблюдение Sync Agent, поэтому открытие меню не обращается к VPS.

```text
НОДЫ

[1] Установить

[2] uk-1 · Великобритания
    194.147.35.112
    healthy · проверена 2 минуты назад

[0] Назад
```

У каждой ноды три смысловые строки: видимый ID и имя, адрес, статус со временем
последней подтверждённой проверки. Номеров у списка столько, сколько нод, поэтому
`2` — первая нода; `0` — назад. Навигация во всех меню нод цифровая: букв `y/n`,
внутренних имён и JSON в обычном пути нет.

**Статус.** `healthy` означает, что последний полный цикл подтверждён: связь есть,
настройки применены, экспорт профилей целый и свежий. `warning` показывает причину —
«нет связи», «применение настроек не выполнено», «профили не опубликованы»,
«обновление не завершено», «проверка устарела». Здоровье контроллера или наличие
указателя публикации само по себе статусом `healthy` не является. Нода, выведенная
из подписки, показывается как «убрана из подписки», а не как сломанная.

Карточка ноды имеет постоянные пункты:

```text
[1] Настройки протоколов
[2] Внешний вид
[3] Синхронизировать
[4] Обновление
[5] Удаление
[0] Назад
```

Номера не зависят от состояния: `5` — это всегда удаление, а не «то, что сейчас
важнее». Причина и следующее действие написаны текстом; SHA, поколения и адрес
control API остаются служебными деталями.

### Установка

Мастер задаёт вопросы в одном порядке: адрес VPS → имя пользователя SSH → пароль SSH
→ видимый ID → имя ноды → меню протоколов → `Готово` → план → подтверждение → лог →
отчёт. Пароль вводится без эха, нигде не сохраняется и передаётся OpenSSH через
одноразовый локальный канал; в state, лог и командную строку он не попадает.

SSH-пользователь по умолчанию `root`. Другой аккаунт используется на всех SSH-этапах;
если он не root, установка до первой мутации проверяет `sudo -n`, а удалённые команды
идут через `sudo -n`. Пароль для `sudo` не предполагается равным паролю SSH: без
passwordless sudo мастер честно отказывает до установки.

Протоколы выбираются номерами и настраиваются в отдельных меню — тем же набором
полей, что и на основе. SSH-порт, порт API управления, ветка и регион не входят
в обязательный опрос: они берутся из значений по умолчанию, а изменить их можно
пунктом «Исправить данные» в плане.

До подтверждения плана ни state, ни VPS не меняются. План показывает адрес, аккаунт,
видимый ID, имя, протоколы, ветку, полный SHA и адрес подписки; пароль в плане
не показывается. Подтверждение числовое (`1`/`0`), по умолчанию — отмена.
После подтверждения экран печатает реальные этапы по мере их выполнения и заканчивается
отчётом: что установлено, подключено, применено и опубликовано.

Установщик идёт потоком по SSH без PTY (`ssh -T`): `bash -s` работает
неинтерактивно, поэтому `set -e`, ERR-trap и отчёт об ошибке действуют, а вывод
остаётся читаемым.

SHA вручную не вводится: после выбора протоколов мастер получает текущий коммит
выбранной ветки (`main` или `dev`) из публичного GitHub API и показывает полный
SHA в плане перед подтверждением. Ответ проверяется на совпадение ветки и полный
40-символьный commit SHA; запрос ограничен 10 секундами и 64 KiB ответа.
При недоступности GitHub, отсутствии ветки или некорректном ответе установка
не начинается. После подтверждения используется именно показанный SHA, без
повторного выбора сдвинувшейся ветки.

Названия протоколов используют общий справочник TUI, даже если плагин не задал
`display_name`; выбранные включённые протоколы отмечены в списке.

Порт мастер не спрашивает: клиенты TLS-протоколов всегда идут на TCP/443, а какой
внутренний порт занять — решает сама нода (`hydra/core/sni_router_planning.py`).
Один TLS-протокол слушает 443 напрямую; несколько — за SNI-мультиплексором, где
у каждого свой фиксированный внутренний порт (AnyTLS 20444, TrustTunnel 20445,
ShadowTLS 20446, NaiveProxy 10443), а SNI выбирает бэкенд. Отдельный порт
задаётся только там, где плагин читает его из своего config: Hysteria2 (UDP,
по умолчанию 8443), VK Tunnel (UDP, 56002) и qWDTT (DTLS, 56000).

У каждого протокола свой набор публичных параметров вместо общего поля JSON
(`hydra/ui/_menus/node_protocol_fields.py`): домен там, где он обязателен,
транспорт (HTTP/2, QUIC, оба), режим XHTTP, отпечаток uTLS, congestion control
Hysteria2, пресеты обфускации AnyTLS/Mieru из реестра плагина, версия AmneziaWG,
обфускация Snell, режим WEB у MTProto Zig, CDN-домен и режим медиа у VLESS CDN.
Числовые поля проверяют диапазон, перечисления выбираются номерами, `0` — отмена,
пустой Enter оставляет текущее значение. Пустой ввод обязательного поля, мусор
в числовом или нераспознанный номер пункта ограничены тремя попытками, после чего
настройка отменяется (или остаётся текущее значение), а не зацикливается.
Секреты (`private_key`, `password`, `token`) этим путём передать
нельзя: таких полей в реестре нет, а контракт ноды отвергает их в config.
Нода создаёт ключи, пароли и сертификаты сама.

При ошибке мастер не заявляет успешную установку; неполный
provisioning требует проверки и повторной попытки с тем же ID.

Параметры нод редактируются этим же набором полей, а не локальными
plugin-wizards основы: последние меняют host основы и потому не вызываются для
удалённой VPS. Если протоколу нужна настройка, которой нет в наборе, она остаётся
на ноде (значение по умолчанию плагина) и не задаётся с основы.

### Настройки протоколов и имена профилей

`1 Настройки протоколов` открывает список протоколов ноды; вход в протокол
предлагает `Настроить параметры` или `Имя профиля в подписке`. Перед сохранением
показываются только изменённые поля, затем — подтверждение. Сохранение запускает
тот же полный цикл синхронизации, что и пункт `3`, поэтому отдельной кнопки
«применить» нет. Если нода недоступна, изменение сохраняется как намерение
и честно показывается как ожидающее применения.

Переключения режимов выполняются владельцем, а не записью ключа в config. Версия
AmneziaWG и VLESS TLS/Reality — это команды плагина: первая поднимает паддинги до
нормы 3.x и создаёт material generation, вторая генерирует пару ключей Reality.
Нода вызывает их сама при расхождении с желаемым состоянием; на хосте без
профилей AWG сначала создаёт первый профиль штатной ротацией обфускации, иначе
переключение generation отказывает. Поэтому `protocol_mode` без локальных
профилей больше не приводит к падению apply.

Желаемое состояние основы владеет только публичными параметрами. Локальный
материал ноды — `profiles` и material generation AmneziaWG, пути сертификатов,
ключи Reality — при слиянии сохраняется: основа не может его перезаписать или
стереть, даже если не передаёт эти ключи.

### Внешний вид

`2 Внешний вид` меняет видимый ID и имя. Видимый ID — это подпись ноды в списке
и подписях; техническая идентичность (сертификаты, ключи, экспорты, счётчики
трафика и идентификаторы клиентских профилей) остаётся прежней. Переименование
не требует связи с нодой и не перевыпускает ни одного ключа. Два узла не могут
иметь одинаковый видимый ID. У нод без заданного ID подписью служит имя или
технический идентификатор.

### Синхронизация

`3 Синхронизировать` запускает полный цикл немедленно, не дожидаясь таймера:
опрос состояния и трафика → учёт квот и блокировок → применение актуального
намерения → обновление профилей в подписках → отчёт. Тот же цикл выполняет
существующий Sync Agent раз в пять минут (`OnCalendar=*:0/5`); отдельного
опросчика нод нет. Повторный или одновременный запрос не запускает вторую
конфликтующую операцию, а повторный отчёт не начисляет трафик дважды.

### Обновление

`4 Обновление` показывает фактически установленную версию и цель разрешённого
канала, требует подтверждения и печатает отчёт. Ручной SHA не спрашивается.
`Запланировано` не считается завершением: карточка покажет установленную ревизию
и результат публикации только после реального обновления. Уже установленная цель
не запускает установщик второй раз.

### Удаление: три разных исхода

```text
[1] Удалить HYDRA с VPS     полная очистка принадлежащей HYDRA установки
[2] Убрать из подписки      на ноде удаляются пользователи и протоколы
[3] Отсоединить             очистки нет, VPS продолжит работать
[0] Назад
```

Все три требуют точного видимого ID и отдельного числового подтверждения; по
умолчанию — отмена.

`1 Удалить HYDRA с VPS` удаляет только принадлежащие HYDRA службы, программу
и данные, а также служебный доступ, и только после этого — локальную запись.
Чужие службы, пользователи и ключи не затрагиваются.

`2 Убрать из подписки` прекращает выдачу сразу и убирает ноду из подписок даже
без связи, а на ноде удаляет пользователей, клиентские credentials и протоколы.
Управление и установленная HYDRA остаются, поэтому ноду можно настроить заново
и вернуть. Это durable-намерение: следующая синхронизация не восстанавливает
пользователей сама. Если нода недоступна, экран говорит «из выдачи убрана,
очистка ожидается», а не «пользователи удалены».

`3 Отсоединить` удаляет только локальные запись, публикацию и credentials.
**Очистка не выполняется: VPS и её службы продолжат работать, а старые клиенты
могут подключаться.** Предупреждение показывается до подтверждения. Очистите или
выключите VPS отдельно.

Перед выводом из подписки и удалением основа делает последнюю попытку учёта
трафика; уже начисленные байты сохраняются в общей квоте.

## Публикация и состояние ноды

Публикация экспорта — это обещание, что подписки действительно увидят профили
ноды. Экспорт без клиентских профилей не публикуется вообще, поэтому «опубликовано
поколение N» всегда означает непустой материал. Неполное покрытие — другой случай:
один транспорт, чьи предпосылки не выполнены (например пул Calls без cookies), не
отбирает у ноды остальные рабочие профили, но виден как предупреждение и как
счётчик по каждому протоколу. Нечитаемый или отсутствующий локальный снимок одной
ноды также не убирает профили остальных нод из подписки.

Рантайм-состояние ноды — доступность, этап и код последней ошибки, время
последней проверки и успеха, применённое и опубликованное поколения, покрытие
профилей — хранится отдельно от `state.json` в `/var/lib/hydra/node-observations.json`.
Это проекция наблюдений, а не желаемая конфигурация: она не увеличивает revision и
может быть удалена без потери настроек. Фоновая сверка (Sync Agent, раз в 5 минут)
обновляет её сама, ручная проверка нужна только для немедленного ответа.

В интерфейсе эти оси не смешиваются: «Связь» говорит только о доступности и о том,
на каком этапе остановилась операция, «Экспорт в подписки» — о публикации и
покрытии, а причина последней ошибки показывается рядом с этапом. «Не проверялась»
означает отсутствие наблюдения, а не недоступность.

Поля протокола спрашиваются только тогда, когда они что-то значат: явные Mbps у
Hysteria2 нужны только в режиме Brutal, домен WEB-ретранслятора — только при
включённом режиме. Значение, которое перестало применяться, удаляется из желаемого
состояния, а не остаётся мусором (выключенный WEB-релей не оставляет за собой
`web_domain`). Невозможные сочетания отсекаются до обращения к VPS: пустой домен в
режиме TLS, WEB-режим без своего домена, совпадение домена релея с доменом FakeTLS.
В режиме Reality домен не обязателен: рукопожатие заимствуется, а своё значение
только заменяет маску по умолчанию.

## Частичная установка и обновление

Если установка дошла до VPS, но удостоверение ноды не выдалось, повторная установка
не нужна и не разрешается: мастер сам предлагает продолжить подключение той же
ноды — HYDRA заходит по pinned SSH и выдаёт удостоверение, не запуская установщик
второй раз. Host key при этом не запрашивается повторно: используется pin,
оставленный первой установкой (`StrictHostKeyChecking=yes`), поэтому подключиться к
другой машине под тем же адресом молча нельзя. Если на VPS нет HYDRA, продолжение
честно падает и нужно добавлять ноду как новую.

Фактическая версия ноды берётся из её собственного маркера
(`/opt/hydra/.hydra-source-revision`), а не из записи основы: запись основы — это
цель, а не факт. Поэтому карточка различает «запланировано», «ожидает» (установлено
одно, запрошено другое) и «выполнено», а завершение обновления подтверждается
совпадением ревизий.
Обновление тоже автоматически получает SHA выбранной ветки из GitHub, показывает
его и требует подтверждения до смены target. Затем сохраняет проверенный target
SHA и планирует штатный upgrade; `scheduled` не означает, что cutover завершился. После завершения проверь
связь и выполни сверку экспорта (она также выполняется в фоне Sync Agent).

## VK cookies и пул звонков

Для Hydra VK Tunnel (`calls`, профиль HydraBox v2) скачайте именно
**WhitelistBypass.Creator** из
[релизов whitelist-bypass](https://github.com/kulikov0/whitelist-bypass/releases)
и получите JSON cookies своего VK-аккаунта. Это секрет: не публикуйте JSON,
не присылайте его в логи и не храните в git. Перенесите выбранный файл на основу
по SCP/SFTP; защищайте его права и удаляйте временные копии.

В карточке ноды выберите «Импорт VK cookies ноды» и укажите путь к отдельному
JSON. Это может быть другой VK-аккаунт: cookies основы автоматически не копируются.
В мастере установки с включённым `calls` путь запрашивается отдельно; файл
валидируется до установки, затем импортируется после provisioning и до первого
применения снимка. При сбое после provisioning запись остаётся для повторного
импорта и сверки из карточки — повторно устанавливать ноду с тем же ID нельзя.

Передача выполняется по pinned SSH без TTY (чтобы терминал не эхоил секретный
stdin), с ограничением JSON до 1 MiB. Импортёр проверяет локальную identity ноды,
валидирует cookies и атомарно заменяет только
`/etc/hydra/cookiesvk/cookies-vk.json` (`0600`, каталог `0700`). Ни cookies, ни путь
исходного файла не попадают в desired state, профили клиентов или argv SSH.
Control API не получает доступа к произвольным файлам.

Импорт сам по себе не создаёт звонки, не перезапускает runtime и не пересоздаёт
существующий пул. При первом включении `calls` нода создаёт собственный пул из
четырёх комнат; это ещё четыре комнаты, а не общий пул основы. Для существующего
пула замена cookies относится к будущим операциям Creator, а не к немедленному
пересозданию. Операция удалённого принудительного пересоздания пула пока не
предоставляется: импорт cookies не следует считать её заменой.

Первое включение и выключение вызывают штатный lifecycle Calls, а не только
общий переключатель протокола. До изменения сохраняется снимок пула; при сбое
lifecycle, проверки экспорта или записи generation восстанавливаются его файлы
и службы, новые принадлежащие пулу артефакты удаляются. Cookies этот rollback
не меняет. Повторное применение уже подтверждённой generation не создаёт новые
комнаты.

## Канал управления

Установка и удаление выполняются по SSH с явно подтверждённым host fingerprint.
Для каждой ноды основа хранит отдельный `known_hosts`; пароль не передаётся в argv
или state. После установки используется ограниченный HTTPS API с взаимным TLS,
проверкой fingerprint сертификата и firewall allowlist IP основы. По умолчанию
management port — TCP/9444; это не порт клиентского протокола.

API предоставляет только health, diagnostics, apply полного снимка, экспорт
клиентских профилей, отчёт трафика и штатное обновление. Он не предоставляет
произвольных команд или доступа к файлам. На самой ноде интерактивный интерфейс
аварийный, только для чтения; обычное управление выполняется на основе.

При подключении ноды основа выдаёт себе отдельный служебный SSH-ключ и добавляет
его в `authorized_keys` с меткой владельца. Дальнейшие обслуживающие операции
(удаление, отзыв удостоверения, импорт cookies) используют этот ключ, поэтому
пароль SSH нужен только на первой установке. Ключ хранится в защищённом каталоге
credentials с правами `0600`, чужие ключи в `authorized_keys` не перезаписываются,
а удаляется только помеченная строка. Если ключ установить не удалось, установка
не считается неуспешной: обслуживание продолжит спрашивать пароль аккаунта.

## Подписки

После подтверждённого применения основа получает персональные клиентские профили
и сохраняет защищённый локальный снимок. Указатель публикации переключается только
после проверки экспорта и записи снимка. Ошибка сверки оставляет последнюю успешную
публикацию.

GET подписки не обращается к нодам. Материалы выбираются по UUID; новый пользователь
не получает профили, пока нода не подтвердила его снимок. Base64, Shadowrocket,
Throne, NekoBox, Sing-box и HydraBox объединяют подходящие профили основы и нод.
Ресурсы и имена нод имеют отдельное пространство имён. Личное имя пользователя
имеет приоритет над общим именем профиля ноды; переименование на основе работает
без связи с нодой.

## Трафик, квоты и сброс

В фоне Sync Agent получает абсолютный накопленный трафик по UUID от каждой ноды,
затем проверяет ограничения на основе. Сетевые запросы выполняются вне блокировки
записи state. После локального sync выполняется best-effort сверка нод, включая
новые блокировки. Повторный или запоздавший отчёт не добавляет те же байты дважды.

На основе локальные байты отделены от вклада каждой ноды. `traffic_used_bytes` и
`Subscription-Userinfo` отражают их сумму. Недоступная нода сохраняет последний
известный вклад; удаление ноды не списывает уже учтённое потребление пользователя.

Сброс квоты повышает эпоху пользователя. Основа немедленно обнуляет текущий период,
а нода сбрасывает локальный накопленный итог при получении нового полного снимка,
сохраняя baselines runtime-счётчиков. Старые отчёты предыдущей эпохи не возвращают
списанный трафик. Epoch привязана к UUID, поэтому переименование не начинает новую
квоту. Общий сброс отчёта трафика не сбрасывает пользовательские квоты.

## Что происходит без связи

Нода продолжает обслуживать клиентов по последней успешно применённой конфигурации.
Изменение пользователя на основе не откатывается из-за недоступности ноды. После
восстановления связи передаётся последний полный снимок, а не очередь команд.

Строгий общий лимит офлайн невозможен: основа не знает новые байты, нода не знает
потребление других серверов и новые блокировки. Возможен перерасход. Сброс на
недоступной ноде начинается при получении новой эпохи, не задним числом в момент
нажатия на основе. Срок действия зависит от корректного времени на ноде.

## Обновление и удаление

Обновление использует конкретный 40-символьный SHA коммита, не подвижную ветку.
Совместимость node contract проверяется до и после переключения; штатный
транзакционный upgrade откатывает неудачное переключение. Текущий wire contract —
5 (включает эпоху сброса и отчёт трафика); это не версия формата state.
См. [UPGRADE.md](UPGRADE.md).

Удаление, вывод из подписки и отсоединение описаны выше, в разделе «Удаление:
три разных исхода». При полном удалении сначала подтверждается успешный uninstall
по pinned SSH, затем удаляются локальное описание ноды и credentials. При ошибке
удалённого uninstall основа сохраняет конфигурацию и credentials для повторной
попытки.

Если VPS недоступна и её необходимо убрать из подписок, используйте «Убрать
из подписки»: нода немедленно исчезает из выдачи, а очистка выполняется при
восстановлении связи. Уже начисленные байты остаются в квоте. Ошибки очистки
локальных файлов показываются отдельно; запись и публикация уже могут быть удалены.

**Вывод из подписки и отсоединение не останавливают удалённую VPS и не отзывают
её старые ключи.** Она может продолжать обслуживать старые профили; новых отчётов
о её трафике основа уже не получит. Очистите или выключите VPS отдельно при
восстановлении доступа. Когда SSH работает, предпочитайте штатное удаление
с очисткой.

Полный сценарий с root/systemd/nftables, установкой, обновлением и удалением требует
изолированной Linux integration-среды. Локальные unit-тесты на Windows её не заменяют.
