# Основа и управляемые ноды

Основа хранит желаемую конфигурацию пользователей и нод. Нода обслуживает клиентов
самостоятельно: серверные ключи, credentials протоколов и runtime-счётчики создаются
и остаются на ней. Общий UUID пользователя служит идентификатором, а не набором
общих секретов.

## Меню основы

Пункт `9 Ноды` открывает список и карточку. Просмотр списка не делает сетевых
запросов; «Проверить связь» — отдельная read-only операция. В карточке доступны
имя/регион, протоколы, имена профилей, диагностика, сверка экспорта, обновление и
удаление. Смена имени не требует доступности ноды. Удаление требует точного имени
и отдельного подтверждения, после чего выполняется pinned SSH cleanup. Отдельные
пункты позволяют импортировать VK cookies выбранной ноды и отсоединить её без
удалённой очистки; отсоединение не останавливает работу VPS.

Мастер требует активного HTTPS-сервера подписок и сертификата основы. Все шаги
до итогового подтверждения только собирают данные; `cancel` отменяет ввод, пункт
`0` отменяет выбор. Указываются SSH/management адрес, порты, имя/регион, ветка и
точный SHA. Для протокола вводятся порт и публичный JSON config, включая домен
клиентского подключения. Приватные ключи/пароли/token в config запрещены контрактом;
нода создаёт их сама. При ошибке мастер не заявляет успешную установку; неполный
provisioning требует проверки и повторной попытки с тем же ID.

Редактор параметров нод сейчас использует JSON, а не локальные plugin-wizards:
последние могут менять host основы и потому не вызываются для удалённой VPS.
Обновление сначала сохраняет проверенный target SHA, затем планирует штатный
upgrade; `scheduled` не означает, что cutover завершился. После завершения проверь
связь и выполни сверку экспорта (она также выполняется в фоне Sync Agent).

## VK cookies и пул звонков

Для Hydra VK Tunnel (`calls`, профиль HydraBox v2) скачайте именно
**WhitelistBypass.Creator** из
[релизов whitelist-bypass](https://github.com/kulikov0/whitelist-bypass/releases)
и получите JSON cookies своего VK-аккаунта. Это секрет: не публикуйте JSON,
не присылайте его в логи и не храните в git. Перенесите выбранный файл на основу
по SCP/SFTP; защищайте его права и удаляйте временные копии.

В карточке ноды выберите «Импорт VK cookies ноды» и укажите путь к отдельному
JSON. Это может быть другой VK-аккаунт: cookies основы автоматически не копируются.
В мастере установки с включённым `calls` путь запрашивается отдельно; файл
валидируется до установки, затем импортируется после provisioning и до первого
применения снимка. При сбое после provisioning запись остаётся для повторного
импорта и сверки из карточки — повторно устанавливать ноду с тем же ID нельзя.

Передача выполняется по pinned SSH без TTY (чтобы терминал не эхоил секретный
stdin), с ограничением JSON до 1 MiB. Импортёр проверяет локальную identity ноды,
валидирует cookies и атомарно заменяет только
`/etc/hydra/cookiesvk/cookies-vk.json` (`0600`, каталог `0700`). Ни cookies, ни путь
исходного файла не попадают в desired state, профили клиентов или argv SSH.
Control API не получает доступа к произвольным файлам.

Импорт сам по себе не создаёт звонки, не перезапускает runtime и не пересоздаёт
существующий пул. При первом включении `calls` нода создаёт собственный пул из
четырёх комнат; это ещё четыре комнаты, а не общий пул основы. Для существующего
пула замена cookies относится к будущим операциям Creator, а не к немедленному
пересозданию. Операция удалённого принудительного пересоздания пула пока не
предоставляется: импорт cookies не следует считать её заменой.

Первое включение и выключение вызывают штатный lifecycle Calls, а не только
общий переключатель протокола. До изменения сохраняется снимок пула; при сбое
lifecycle, проверки экспорта или записи generation восстанавливаются его файлы
и службы, новые принадлежащие пулу артефакты удаляются. Cookies этот rollback
не меняет. Повторное применение уже подтверждённой generation не создаёт новые
комнаты.

## Канал управления

Установка и удаление выполняются по SSH с явно подтверждённым host fingerprint.
Для каждой ноды основа хранит отдельный `known_hosts`; пароль не передаётся в argv
или state. После установки используется ограниченный HTTPS API с взаимным TLS,
проверкой fingerprint сертификата и firewall allowlist IP основы. По умолчанию
management port — TCP/9444; это не порт клиентского протокола.

API предоставляет только health, diagnostics, apply полного снимка, экспорт
клиентских профилей, отчёт трафика и штатное обновление. Он не предоставляет
произвольных команд или доступа к файлам. На самой ноде интерактивный интерфейс
аварийный, только для чтения; обычное управление выполняется на основе.

## Подписки

После подтверждённого применения основа получает персональные клиентские профили
и сохраняет защищённый локальный снимок. Указатель публикации переключается только
после проверки экспорта и записи снимка. Ошибка сверки оставляет последнюю успешную
публикацию.

GET подписки не обращается к нодам. Материалы выбираются по UUID; новый пользователь
не получает профили, пока нода не подтвердила его снимок. Base64, Shadowrocket,
Throne, NekoBox, Sing-box и HydraBox объединяют подходящие профили основы и нод.
Ресурсы и имена нод имеют отдельное пространство имён. Личное имя пользователя
имеет приоритет над общим именем профиля ноды; переименование на основе работает
без связи с нодой.

## Трафик, квоты и сброс

В фоне Sync Agent получает абсолютный накопленный трафик по UUID от каждой ноды,
затем проверяет ограничения на основе. Сетевые запросы выполняются вне блокировки
записи state. После локального sync выполняется best-effort сверка нод, включая
новые блокировки. Повторный или запоздавший отчёт не добавляет те же байты дважды.

На основе локальные байты отделены от вклада каждой ноды. `traffic_used_bytes` и
`Subscription-Userinfo` отражают их сумму. Недоступная нода сохраняет последний
известный вклад; удаление ноды не списывает уже учтённое потребление пользователя.

Сброс квоты повышает эпоху пользователя. Основа немедленно обнуляет текущий период,
а нода сбрасывает локальный накопленный итог при получении нового полного снимка,
сохраняя baselines runtime-счётчиков. Старые отчёты предыдущей эпохи не возвращают
списанный трафик. Epoch привязана к UUID, поэтому переименование не начинает новую
квоту. Общий сброс отчёта трафика не сбрасывает пользовательские квоты.

## Что происходит без связи

Нода продолжает обслуживать клиентов по последней успешно применённой конфигурации.
Изменение пользователя на основе не откатывается из-за недоступности ноды. После
восстановления связи передаётся последний полный снимок, а не очередь команд.

Строгий общий лимит офлайн невозможен: основа не знает новые байты, нода не знает
потребление других серверов и новые блокировки. Возможен перерасход. Сброс на
недоступной ноде начинается при получении новой эпохи, не задним числом в момент
нажатия на основе. Срок действия зависит от корректного времени на ноде.

## Обновление и удаление

Обновление использует конкретный 40-символьный SHA коммита, не подвижную ветку.
Совместимость node contract проверяется до и после переключения; штатный
транзакционный upgrade откатывает неудачное переключение. Текущий wire contract —
5 (включает эпоху сброса и отчёт трафика); это не версия формата state.
См. [UPGRADE.md](UPGRADE.md).

При удалении сначала подтверждается успешный uninstall по pinned SSH, затем
удаляются локальное описание ноды и credentials. При ошибке удалённого uninstall
основа сохраняет конфигурацию и credentials для повторной попытки.

Если VPS недоступна и её необходимо убрать из подписок, используйте отдельный
пункт «Отсоединить без очистки VPS»: точное имя ноды и дополнительное подтверждение
обязательны. Удаляются запись и указатель публикации на основе, локальный экспорт,
control credentials и pinned host key; уже начисленные байты остаются в квоте.
SSH и control API не вызываются. Ошибки очистки локальных файлов показываются
отдельно; запись и публикация уже могут быть удалены.

**Отсоединение не останавливает удалённую VPS и не отзывает её старые ключи.**
Она может продолжать обслуживать старые профили; новых отчётов о её трафике
основа уже не получит. Очистите или выключите VPS отдельно при восстановлении
доступа. Когда SSH работает, предпочитайте штатное удаление с очисткой.

Полный сценарий с root/systemd/nftables, установкой, обновлением и удалением требует
изолированной Linux integration-среды. Локальные unit-тесты на Windows её не заменяют.
