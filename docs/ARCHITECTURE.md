## 1. Модель системы

HYDRA — оркестратор многопротокольного прокси-сервера. Пользовательские данные и
настройки хранятся в `state.json`, а рабочие конфигурации служб создаются из него
через единый прикладной и оркестрационный слой.

```text
┌────────────────────────────────────────────────────────────┐
│ TUI · CLI · Telegram · будущие API-адаптеры                │
└──────────────────────────────┬─────────────────────────────┘
                               │ прикладные службы
┌──────────────────────────────▼─────────────────────────────┐
│ ApplicationService · ProtocolService · UserService         │
└──────────────────────────────┬─────────────────────────────┘
                               │ оркестратор транзакций
┌──────────────────────────────▼─────────────────────────────┐
│ ConfigurationApplier · PluginLifecycle · UserLifecycle     │
└──────────────────────────────┬─────────────────────────────┘
                               │ HostBackend
┌──────────────────────────────▼─────────────────────────────┐
│ systemd · файлы · сетевые инструменты · команды хоста      │
└────────────────────────────────────────────────────────────┘
```

Слой представления не должен напрямую управлять `systemd`, межсетевым экраном,
файлами конфигурации или отдельными плагинами. Такие действия проходят через
прикладные службы, оркестратор и `HostBackend`.

Конкретные границы кода:

- `hydra.ui.menus` — совместимый фасад TUI; контроллеры ядра, протоколов,
  пользователей, Telegram, мониторинга и безопасности находятся в
  `hydra.ui._menus`;
- CLI, TUI, Telegram, фоновые workers и plugin-specific managers вызывают
  `ApplicationService`, а не функции `core.orchestrator`;
- `hydra.core.orchestrator` сохраняет старый публичный API, lock и журнал, но
  делегирует работу в `services.configuration`, `services.plugin_lifecycle`,
  `services.user_lifecycle` и `services.traffic_daemon_unit`;
- `plugins.registry` — совместимый фасад над `PluginCatalog`, `PluginExecutor`
  и единым `PluginInvoker`.

### Направление зависимостей

Слои кода образуют однонаправленный граф. Стрелка означает «имеет право
импортировать»; обратного пути нет, и цикл считается ошибкой архитектуры.

```text
   entrypoints        ui                    Разрешено:  A ──▶ B
        │             │                     Запрещено:  A ◀── B
        └──────┬──────┘
               ▼
           services ──────────────┐
               │                  │
               ▼                  ▼
           plugins ──────────▶ contracts
               │                  ▲
               ▼                  │
             core ────────────────┘

   contracts  не зависит ни от кого — нейтральные типы
   core       не импортирует верхние слои
   plugins    не импортируют services и entrypoints
   services   не импортируют ui и entrypoints
```

Единственные исторические исключения — тонкие compatibility-фасады
`hydra.core.orchestrator`, `hydra.plugins.registry` и `hydra.ui.menus`, а также
явно разрешённый Telegram-entrypoint. Новый код на них опираться не должен.

Production-сборка приложения находится только в
`hydra.bootstrap.production_application()`. Process-global `ApplicationService`,
`PluginInvoker` или новый глобальный реестр плагинов создавать нельзя:
зависимости передаются явно.

### Какие отказы устраняет модель

Тот же результат достижим вручную — Sing-Box, Caddy, certbot, nftables, ipset,
Fail2ban, systemd-units и скрипты учёта трафика. Сложность возникает не при
первичной настройке, а при каждом последующем изменении. Инварианты ниже
существуют ради конкретных отказов эксплуатации.

| Отказ ручной сборки | Механизм HYDRA |
| :--- | :--- |
| Сменили домен — state и Caddy разошлись, доменные транспорты молчат | Домены производны от state; расхождение SNI видно как блок `tls_mux` и лечится повторным `apply` |
| Правка применилась наполовину: Sing-Box перезапущен, nftables нет | Каждый изменяющий шаг имеет снимок и rollback: возвращаются state, конфигурации, firewall и плагины |
| Два QUIC-транспорта незаметно заняли UDP/443 | Конфликт слушателей отклоняется на preflight, а не проявляется отказом в рантайме |
| Служба показана «включённой», хотя не работает | Желаемое и фактическое разделены: `hydra status` показывает оба и расхождение между ними |
| Обновление сводится к `git pull`, старый код получает state новой схемы | Транзакционный updater: сборка рядом с рабочей, read-only preflight, два уровня backup, атомарное переключение, откат |
| Пользователь добавлен в один транспорт и забыт в остальных | Добавление пользователя — транзакция по всем включённым транспортам сразу |
| Сканирование ловится разрозненно, ложные баны блокируют своих | Единый контур корреляции с двухуровневым scoring; подделываемые UDP-сигналы не дают автоматического бана |

## 2. Пути входящего трафика

### TCP/443 и SNI

Caddy L4 используется, когда нужен общий TCP/443: включён AnyTLS, TrustTunnel,
Hysteria2 или VLESS + XHTTP с доменом, одновременно работают несколько
TLS-транспортов либо задан домен сервера подписок.

- **NaiveProxy** и **ShadowTLS** проходят через мультиплексор сквозняком, без
  расшифровки в Caddy L4. У NaiveProxy при этом есть собственный домен и
  сертификат — TLS для него завершает отдельная служба `caddy-naive`.
- **AnyTLS** завершает TLS в Caddy, затем разделяет протокольный поток и обычный
  HTTP-запрос к сайту-заглушке.
- **TrustTunnel** завершает TLS и отправляет CONNECT во внутренний
  HTTP-адаптер; обычные запросы направляются на сайт-заглушку.
- TCP-маршрут домена **Hysteria2** обслуживает сайт-заглушку; сам Hysteria2
  работает по UDP на своём порту.
- **VLESS + XHTTP** завершает внешний TLS в Caddy. Запросы на настроенный
  XHTTP-путь проксируются по HTTP/2 с повторным TLS во внутренний VLESS inbound
  Sing-Box Extended; остальные URL обслуживает отдельная media-заглушка.
- Для неизвестного SNI используется резервный маршрут только при наличии
  соответствующей активной заглушки.

Ключевое различие — где именно завершается TLS:

```text
                     ┌──────────────── Caddy L4 · TCP/443 ────────────────┐
                     │                                                    │
  ClientHello ──────▶│  читает SNI, не расшифровывая полезную нагрузку    │
                     │                          │                         │
                     │        ┌─────────────────┴─────────────────┐       │
                     │        ▼                                   ▼       │
                     │  TLS завершается здесь              сквозной TLS   │
                     │  ┌──────────────────┐              ┌────────────┐  │
                     │  │ AnyTLS           │              │ ShadowTLS  │  │
                     │  │ TrustTunnel      │              │ NaiveProxy │  │
                     │  │ Hysteria2 (TCP)  │              └──────┬─────┘  │
                     │  │ VLESS + XHTTP    │                     │        │
                     │  └────────┬─────────┘                     │        │
                     │           │                               │        │
                     │  протокольный поток ──▶ backend           │        │
                     │  обычный HTTP ────────▶ сайт-заглушка     │        │
                     └───────────────────────────────────────────┼────────┘
                                                                 ▼
                                                     транспорт сам разбирает TLS
```

Важно не путать два независимых вопроса: **кому нужен свой домен** и **где
завершается TLS**.

| Транспорт | Свой домен | Где завершается TLS |
| :--- | :--- | :--- |
| AnyTLS | нужен (`protocol`) | в Caddy L4 |
| TrustTunnel | нужен (`protocol`) | в Caddy L4 |
| Hysteria2 | нужен (`protocol`) | в Caddy L4 — только TCP-заглушка домена |
| VLESS + XHTTP | нужен (`protocol`) | в Caddy L4, затем повторный TLS до Sing-Box |
| NaiveProxy | нужен (`network`) | в собственном `caddy-naive` |
| ShadowTLS | не нужен | у самого транспорта |

NaiveProxy требует домен и сертификат ровно так же, как остальные
TLS-транспорты, — он объявляет `needs_domain` и берёт домен из сетевых настроек
(`tls_domain_source=network`, тогда как у AnyTLS, TrustTunnel, Hysteria2 и
VLESS + XHTTP домен протокольный). Отличается только место терминации:
L4-мультиплексор передаёт его поток сквозняком, а TLS завершает отдельная служба
`caddy-naive`.

Единственное настоящее исключение — **ShadowTLS**: собственного домена у него нет,
он маскируется под чужой handshake SNI, который задаётся командой
`set_handshake_sni`.

Пару сертификат + ключ Caddy L4 загружает для `anytls`, `trusttunnel`,
`hysteria2` и для plugin-owned HTTP-маршрутов вроде VLESS + XHTTP. Последние
объявляют внутренний порт, decoy-порт, каталог, тему и имя настройки пути через
`PluginMeta.config_defaults`; core валидирует эту декларацию без таблицы по
имени плагина. Маршрут с завершением TLS не рендерится, если пара неполная.

### UDP/443 и QUIC

UDP/443 нельзя распределить по SNI. Прямым владельцем этого порта может быть
только один QUIC-транспорт — NaiveProxy или TrustTunnel; конфликт отклоняется до
применения конфигурации.

Hysteria2 владельцем UDP/443 не является: его UDP-порт и TCP-заглушка
управляются отдельно.

Перед общим `apply` TLS-preflight повторно проверяет сертификаты всех включённых
доменных транспортов: SAN, остаточный срок действия и соответствие приватному
ключу. Caddy-маршрут с завершением TLS не рендерится без полной проверенной пары.

### Остальные входы

AmneziaWG и qWDTT создают туннельные интерфейсы, Mieru и Snell работают как
отдельные входящие подключения, а Telemt обслуживает MTProto. Sing-Box применяет
общие правила маршрутизации, DNS и исходящие соединения ко всем потокам, которые
входят в его контур.

Полная карта портов — в [REFERENCE.md](REFERENCE.md#сетевые-порты).

## 3. TLS-мультиплексор как контролируемый артефакт

Источник истины для доменов — state, а рабочий артефакт —
`/etc/caddy-l4/config.json`. После изменения домена или транспорта выполняется:

```bash
hydra check
sudo hydra apply
hydra status
```

`hydra status` и `hydra check` содержат блок `tls_mux`, который сравнивает
ожидаемое множество SNI с фактическим:

```text
        ожидается по state              фактически в Caddy
     ┌────────────────────┐          ┌────────────────────┐
     │ a.example.com      │◀────────▶│ a.example.com      │  совпадает
     │ b.example.com      │◀───╳     │                    │  missing
     │                    │     ╳───▶│ old.example.com    │  stale
     │ c.example.com      │◀────────▶│ c.example.com      │  certificate_errors
     └────────────────────┘          └────────────────────┘  (нет пары ключей)
```

| Поле | Значение |
| :--- | :--- |
| `missing` | Домен есть в state, но отсутствует в Caddy |
| `stale` | В Caddy остался домен, которого больше нет в state |
| `certificate_errors` | Отсутствует сертификат/ключ либо активный Caddy config не загрузил их пару |
| `errors` | Повреждён JSON конфигурации или неактивен `caddy-l4` |

Проверка только читает данные. Исправление выполняется через транзакционный
`apply`: HYDRA создаёт временный конфиг, запускает проверку Caddy и откатывает
изменения при неудаче.

Для VLESS + XHTTP health-этап дополнительно требует декларативный route,
совпадение домена с активным SNI-маршрутом и успешный локальный TLS handshake
через `127.0.0.1:443` с SNI домена и ALPN `h2`. Поэтому `enable` не может
завершиться успехом при запущенном, но оставшемся на старом конфиге Caddy.

TLS-маршруты проверяются отдельно, потому что они являются самым чувствительным
артефактом системы: ошибка в них означает потерю доступа ко всем доменным
транспортам одновременно.

## 4. Жизненный цикл применения

Применение — это транзакция. Каждый шаг, меняющий систему, сначала сохраняет
снимок, поэтому у отката всегда есть куда вернуться.

```text
   шаг                                        снимок     откат при сбое
   ─────────────────────────────────────────────────────────────────────
   state.json
     │
  1  ├─ проверка и миграция схемы              —          прервать сразу
  2  ├─ сбор ConfigFragment от плагинов        —          прервать сразу
  3  ├─ генерация и валидация Sing-Box       ┌─ ✓ ─┐          ▲
  4  ├─ применение nftables / TPROXY         │  ✓  │          │
  5  ├─ применение включённых плагинов       │  ✓  │          │  откат идёт
  6  ├─ перезагрузка Sing-Box                │  ✓  │          │  в обратном
  7  ├─ пересборка и проверка Caddy L4       │  ✓  │          │  порядке
  8  ├─ согласование учёта трафика           └─ ✓ ─┘          │  8 ─▶ 3
  9  ├─ проверка работоспособности          read-only          │
     │                                                        │
 10  └─┬─ всё успешно ──▶ commit: state сохранён              │
       └─ любой сбой ───▶ rollback ───────────────────────────┘
```

Шаги 1–2 ничего не меняют на хосте, поэтому их сбой просто прерывает операцию.
Начиная с шага 3 каждая мутация имеет снимок и rollback-callback с явным
приоритетом.

Откат обладает тремя свойствами, которые важнее скорости:

- **обратный порядок** — сначала отменяется последнее применённое изменение;
- **продолжение после локальной ошибки** — если один шаг откатить не удалось,
  остальные всё равно откатываются, а исходная причина не теряется;
- **однократность** — повторный запуск отката для той же транзакции невозможен.

При критическом сбое восстанавливаются state, Sing-Box, nftables, плагины и
связанные рабочие файлы. Каждое событие транзакции попадает в
`/var/log/hydra/apply.jsonl`.

`hydra apply --dry-run` является полным эквивалентом `hydra check`: строит план
на копии state и не выполняет изменяющих систему этапов. `status` и read-only
проекции плагинов также не меняют систему.

## 5. Контракты плагинов

Плагин описывает свои возможности, зависимости, фрагмент конфигурации, жизненный
цикл и проверку работоспособности. Реестр проверяет этот контракт до выполнения
команд на хосте.

Плагин видит не весь `AppState`, а узкое окно, и влияет на итоговую конфигурацию
единственным способом — возвращая типизированный фрагмент:

```text
   AppState                        плагин                    общий apply
  ┌──────────────────┐        ┌───────────────────┐      ┌────────────────────┐
  │ protocols  ──────┼───────▶│ PluginStateAccess │      │                    │
  │ users      ──────┼───────▶│  (только чтение)  │      │  сбор фрагментов   │
  │ network    ──────┼───────▶│                   │      │         │          │
  │                  │        │   configure() ────┼─────▶│  ConfigFragment    │
  │ telegram   ──╳   │        │                   │      │   · inbounds       │
  │ install    ──╳   │        │   apply()         │      │   · outbounds      │
  │ revision   ──╳   │        │   health()        │      │   · route_rules    │
  └──────────────────┘        └───────────────────┘      │   · endpoints      │
                                                         │   · dns            │
   ╳ — недоступно плагину                                │   · nft_tproxy_*   │
                                                         │         │          │
                                                         │  валидация JSON,   │
                                                         │  проверка портов,  │
                                                         │  конфликты слушат. │
                                                         │         ▼          │
                                                         │  итоговый          │
                                                         │  config.json       │
                                                         └────────────────────┘
```

Плагин не пишет в итоговый `config.json` напрямую — это делает общий applier
после валидации. Разделение ролей внутри контракта:

```text
   command   изменяет желаемую конфигурацию плагина ──▶ persist и apply
             выполняет прикладная служба, не плагин

   query     read-only проекция, клиентский профиль ──▶ ничего не меняет

   action    явная runtime-операция ─────────────────▶ без общего apply

   lifecycle install · uninstall · enable · disable ──▶ typed result,
             без цепочных вызовов других lifecycle hooks
```

- Базовый контракт принимает `PluginStateAccess`, который открывает только
  `protocols`, `users` и `network`, а не весь persisted `AppState`.
- `PluginMeta.contract_version` делает миграцию контракта явной, а
  `PluginInvoker` централизует dispatch и проверку версии.
- Имя для UI, источник подключений, фоновые задачи и backup-ресурсы объявляются
  в `PluginMeta`; общие сервисы не ветвятся по имени конкретного плагина.
- Изменяющие конфигурацию helper-методы конкретных плагинов являются внутренней
  границей адаптера и требуют явный `apply_configuration`; скрытый service
  locator внутри plugin domain запрещён. Совместимые TUI-входы остаются в
  `hydra.ui.menus` и передают callback из `ApplicationService`.
- Типизированный `ConfigFragment` не допускает произвольные значения Python.
- `configure` подготавливает данные, `apply` применяет их, а `health`
  подтверждает работоспособность.
- Автономные компоненты объявляют `central_apply=False` и не перезапускаются
  общим `apply`, если это не требуется их собственным жизненным циклом. Сейчас
  так работают Honeypot и AntiDPI.
- Старые обработчики с результатом `bool` или `tuple` поддерживаются адаптерами;
  новый код должен возвращать формализованные результаты.

Поддерживаемый путь расширения — в
[PLUGIN_DEVELOPMENT.md](PLUGIN_DEVELOPMENT.md).

## 6. State и рабочее состояние

`state.json` содержит только желаемую и долговечную конфигурацию. Факты вроде
`running`, `health` и рассинхронизации вычисляются отдельно через
`RuntimeSnapshot`.

```text
        желаемое (persisted)                фактическое (вычисляется)
   ┌─────────────────────────────┐     ┌─────────────────────────────┐
   │  /var/lib/hydra/state.json  │     │       RuntimeSnapshot       │
   │                             │     │                             │
   │  protocols[*].enabled       │     │  running                    │
   │  protocols[*].installed     │     │  health                     │
   │  users, network, telegram   │     │  drift                      │
   │  revision                   │     │                             │
   └─────────────┬───────────────┘     └──────────────┬──────────────┘
                 │                                    │
                 └────────────┬───────────────────────┘
                              ▼
                      hydra status · check
                  показывают обе стороны и расхождение

   ╳ факты рантайма никогда не записываются в state как истина
```

> [!WARNING]
> Не исправляйте фактическое состояние правкой `state.json`. «Выключено» в state
> и работающая служба на хосте не противоречат друг другу — это
> рассинхронизация, которую показывает `hydra status` и устраняет `hydra apply`.

Хранилище использует:

- последовательные миграции схемы `vN → vN+1`;
- атомарную замену и синхронизацию каталогов;
- безопасный отказ при неизвестной будущей схеме;
- резервные и изолированные копии при повреждении;
- проверку данных до записи;
- монотонную `revision` и optimistic concurrency: устаревшая запись желаемой
  конфигурации отклоняется, а фоновые счётчики сохраняются атомарно без
  увеличения ревизии;
- откат желаемого состояния с сохранением текущей ревизии, чтобы rollback не мог
  затереть более новое изменение другого процесса.

### Цепочка миграций

В текущей ветке `dev` актуальна схема 8. Миграция — последовательность чистых функций; каждая
ступень проверяется отдельно, а запись всей цепочки выполняется атомарно.

```text
   v0 ──▶ v1 ──▶ v2 ──▶ v3 ──▶ v4 ──▶ v5 ──▶ v6 ──▶ v7 ──▶ v8+
                         │      │      │      │      │
                         │      │      │      │      └─ Headless Creator получает
                         │      │      │      │         provider-neutral state;
                         │      │      │      │         v9+ — ошибка совместимости
                         │      │      │      └─ legacy VK creator state через Calls
                         │      │      └─ private per-user HydraBox JWE key
                         │      │
                         │      └─ device_limit, devices        (выпущено в 2.5.3)
                         └──────── legacy-флаги WARP, DNSCrypt,
                                   Fail2ban, Honeypot, IPBan, AntiDPI
                                   ──▶ protocols[*].enabled, + revision
```

Старый код не должен увидеть state новой схемы — поэтому откат обновления
возвращает схему прежде, чем вернуть код (см. [§8](#8-release-и-обновление)).

### Конкурентная запись

`revision` монотонна и защищает от потери чужих изменений. Устаревшая запись
желаемой конфигурации отклоняется как retryable-конфликт:

```text
   TUI                       state.json                    traffic daemon
    │                      revision = 7                          │
    │── читает rev 7 ────────────▶│◀──────── читает rev 7 ────────│
    │                             │                              │
    │                             │◀── update_state(счётчик) ─────│
    │                      revision = 7   ← фоновые счётчики      │
    │                      (не растёт)      не создают конфликт   │
    │                             │                              │
    │── save_state(rev 7) ───────▶│                              │
    │                      revision = 8                          │
    │                             │                              │
    │  второй писатель с rev 7 ──▶│──▶ ╳ StateConflictError       │
    │                             │     перечитать и повторить    │
```

Rollback восстанавливает содержимое снимка, но сохраняет текущую ревизию —
иначе откат мог бы затереть более новое изменение другого процесса.

> [!WARNING]
> Нельзя исправлять фактическое состояние ручной записью в state. Сначала нужно
> выяснить причину рассинхронизации через `hydra status` и `hydra check`.

Состав файлов состояния — в
[REFERENCE.md](REFERENCE.md#состояние-в-varlibhydra).

## 7. Безопасность и доступ

- Все привилегированные команды проходят через `HostBackend` и имеют таймаут.
- Конфигурации и state записываются атомарно; секреты не выдаются в безопасном
  публичном статусе.
- Пароли, токены, UUID, PSK и приватные ключи заменяются на `[REDACTED]` в
  публичном статусе, выводе CLI и диагностических архивах.
- Backup-policy составляется из доверенных ресурсов ядра и деклараций
  `PluginMeta.backup_resources`. Backup содержит манифест, размер и SHA-256.
  Restore разрешает только точный файл либо рекурсивно принадлежащее дерево,
  проверяет дубликаты, выход за разрешённые пути и симлинки, а перед записью
  создаёт страховочную копию по той же policy.
- `reconcile --apply` исправляет только безопасную рассинхронизацию
  enable/disable; он не устанавливает пакеты и не делает рискованных
  предположений.
- Токен Telegram-бота является root-equivalent секретом — см.
  [TELEGRAM_BOT.md](TELEGRAM_BOT.md).

Поведенческий контур обнаружения разведки описан в [ANTIDPI.md](ANTIDPI.md).
Система не обещает обнаружения любой атаки, защиты от украденных credentials,
различения клиентов за одним NAT и фильтрации объёмного DDoS — последнее должно
выполняться у провайдера до VPS.

## 8. Release и обновление

Постоянные systemd units ссылаются на стабильный `/opt/hydra` и интерпретатор
`/opt/hydra/.venv/bin/python`, а не на физический release-каталог:

```text
   systemd units ──▶ /opt/hydra ──симлинк──▶ /opt/hydra-releases/<sha>-<stamp>
                          ▲                            │
                          │                            └─ .venv, код
                          │
             переключается атомарной заменой симлинка,
             сами unit-файлы при обновлении не меняются

   /opt/hydra-releases/
   ├── <sha-A>-...        ← предыдущий release, остаётся после обновления
   └── <sha-B>-...        ← новый release, собран до остановки служб
```

Благодаря этому новый код и зависимости собираются заранее, а простой
ограничивается временем перезапуска служб HYDRA.

Публичный `updater.sh` полностью загружает `upgrade.sh` до исполнения.
`upgrade.sh` остаётся транзакционным ядром развёртывания:

```text
   1  resolve SHA                    read-only, безопасно прервать
   2  stage release + .venv          read-only для рабочей установки
   3  read-only preflight            новый код читает действующий state
   ─────────────────────────────  точка невозврата  ─────────────────────────
   4  quiesce HYDRA writers          службы и таймеры остановлены
   5  backup raw state + архив       два независимых уровня отката
   6  migrate state                  схема поднята до целевой
   7  switch /opt/hydra              атомарная замена симлинка
   8  restart + validate             ранее активные units подняты и проверены
```

Шаги 1–3 можно прервать без последствий. Сбой после шага 4 запускает откат в
строго определённом порядке:

```text
   остановить новый runtime
        ▼
   вернуть state в старую схему        ◀── обязательно раньше кода
        ▼
   вернуть код и wrapper
        ▼
   запустить ранее активные units из active-units.txt
```

Порядок принципиален: старый код не должен получить state новой схемы. Обратная
последовательность привела бы к загрузке несовместимого состояния прежним
runtime.

Подробная процедура — в [UPGRADE.md](UPGRADE.md).

## 9. Мониторинг и диагностика

Минимальный набор для проверки работающей системы:

```bash
hydra status
hydra check
journalctl -u sing-box -u caddy-l4 --no-pager -n 100
```

Для автоматизации используйте `--json`, поля JSON и `error_details`, а не только текст
ошибки. Полное описание команд — в [CLI.md](CLI.md).

Фоновый sync agent раз в сутки проверяет сроки всех настроенных TLS-сертификатов
и записывает результат в state. Сама проверка read-only и никогда не запускает
изменяющую команду.

Продление идёт двумя путями, потому что у сертификатов два владельца:

- сертификат протокола обновляет общий apply — проверка ставит отложенное
  применение, а preflight переполучает материал через certbot;
- сертификат сервера подписок не принадлежит плагину и в preflight не попадает,
  поэтому проверка выпускает его напрямую и перезапускает `hydra-sub`.

Неудачное продление снимает отложенное применение и ждёт следующей суточной
проверки: certbot на каждой попытке останавливает TLS-фронт, а Let's Encrypt
ограничивает число неуспешных валидаций.

VK Calls — application-owned use-case. `ApplicationService.calls` координирует
lifecycle плагина `calls`, отдельный managed creator-пул и общий apply.
Установка creator и credentials не принадлежат протоколу:
`ApplicationService.headless_creator` владеет provider-neutral lifecycle и
единственным VK cookie-файлом `/etc/hydra/cookiesvk/cookies-vk.json`. Через
внедрённый `CallConfigSource` плагин читает только готовность точного Hydracore
контракта и join-links managed-пула. Профиль admin joiner остаётся
application-owned ручным артефактом. Отдельно плагин владеет
remote-safe joiner-проекцией: при включённом Calls она попадает в Hydra
Subscription v2 как изолированный `call` outbound с `platform=vk` и
`network.outbound`, но без серверных cookies. Пул join-links обязателен и
считается секретом; неполная проекция отклоняет всю выдачу fail-closed.
Клиентский joiner
не становится источником server-side traffic accounting.

Calls имеет только режим `multi_user`. До любых host-мутаций service требует
desired `kernel.provider=hydracore`, exact identity
`io.hydrabox.hydracore`, role `vps`, server feature
`call_vk_multi_user_server=true`, `protocols.call_modes=["multi_user"]` и wire
compatibility v1..2; stock core, client artifact, capability aliases и `p2p`
отклоняются fail-closed. Затем service создаёт отдельную managed-группу 1–4
комнат. Plugin возвращает server inbound с
`listen/listen_port`, общим `obfs_password`, per-user credentials и bounded
session/worker/handshake limits; cookies и join-links в server config
отсутствуют. Per-user Hydra v2 projection содержит `server/server_port`,
`join_links`, user/password, общий obfs key и worker policy и требует core
feature `call_vk_multi_user`; singular `join_link` не генерируется в outbound.
`server` берётся из persisted `calls.config.public_endpoint`, который
материализуется при enable/reinstall из явного `network.server_ip` либо
наблюдаемого публичного IP VPS и никогда не наследует transport SNI.
Admin DTO сохраняет первый link под старым именем только как compatibility alias. Worker policy
по умолчанию создаёт один worker
на ссылку и ограничивает явное значение как
`min(max_workers_per_session, 27 × unique_join_links, 108)`. IPv4 listener по
умолчанию использует свободный `56002/udp`; совпадение с внешними UDP-портами
enabled transport отклоняется до apply (в частности, qWDTT сохраняет
`56001/udp` для WireGuard).

Managed Calls использует собственные
`hydra-headless-creator-vk-calls@{a,b}-N`, поэтому lifecycle qWDTT его не
затрагивает. Новое поколение создаётся до metadata commit, затем общий apply
проверяет server inbound, и только finalize останавливает прежние units. Ошибка
до finalize откатывает pool, state и Sing-Box runtime.

Оба потребителя используют `CreatorSessionManager`. Запрос содержит provider,
consumer, lifetime и количество сессий; manager валидирует его и делегирует
provider driver. Calls и qWDTT запрашивают изолированные `managed`-группы и
самостоятельно владеют desired state,
публикацией артефакта, commit/finalize и rollback. Добавление WB Stream требует
нового driver и consumer use-case, но не ветвления в Calls или qWDTT.
qWDTT-транзакции дополнительно сериализуются между TUI и Sync Agent через
`/run/lock/hydra-creator.lock`.

qWDTT использует того же standalone creator. Два поколения
`hydra-headless-creator-vk@{a,b}-N` позволяют создать от 1 до 16 новых комнат, пока
старые продолжают обслуживать master-ссылку. Только после атомарной публикации
WDTT-артефакта и сохранения state старое поколение останавливается. WDTT
объявляет лишь action преобразования упорядоченного списка уникальных хэшей в
`qwdtt://` и не содержит
lifecycle, timer или systemd creator. Owner-neutral maintenance-фасад объединяет
plugin tasks и `headless_creator.consumers.qwdtt`; его читают Sync Agent и TUI.

Миграция schema 8 извлекает legacy creator desired state из `calls.config`, а
schema 9 отделяет qWDTT consumer state в `headless_creator.consumers.qwdtt` от
provider configuration. Миграции не меняют host runtime. Явное действие
`Создать комнаты` в qWDTT-подменю Creator делает snapshot старых units/файлов,
устанавливает новый пул и только затем удаляет legacy creator; failure
восстанавливает snapshot. Общие VK cookies при этом не удаляются.

Schema 10 добавляет desired `kernel.provider/channel`, оставляет прежний Calls
в историческом `p2p` и материализует qWDTT port defaults для межсервисного
preflight. Schema 11 нормализует любой legacy/unknown Calls mode в `multi_user`;
несовместимый enabled Calls (включая stock core) выключается без удаления
installed state, поэтому upgrade/apply остальных протоколов остаётся доступен.
Повторная установка после switch на Hydracore создаёт новый managed-пул.
`ApplicationService.kernel` — единственный use-case замены core:
trusted release metadata и обязательный SHA-256 digest проверяются до ELF,
identity/capabilities и active-config probe; затем binary меняется атомарно,
служба проходит bounded health, и только после этого сохраняется state. Ошибка
копирования, старта или persistence восстанавливает прежний binary и состояние
службы. Legacy stock installer не перезаписывает выбранный Hydracore.

Cookies и join-links не хранятся в state и не попадают в status/apply journal.
Лог-проекции HYDRA редактируют VK и qWDTT links. Upstream Sing-Box выводит
join-links на уровне INFO, поэтому сырой journald остаётся секретным источником.

`PluginMeta.manual_artifacts_query` отделяет административные ручные артефакты
от per-user подписок. qWDTT объявляет через него единственную master-ссылку для
экрана «Ручные конфиги», сохраняя `subscription_enabled=False`: ссылка содержит
главный пароль, является общей и не должна попадать в subscription API.
`hydra_v2_subscription_enabled` также остаётся `False`, поэтому Hydra v2
renderer не вызывает qWDTT client hook даже при включённом протоколе. Native
Calls задаёт обратную комбинацию: legacy subscriptions выключены, а только
Hydra v2 projection включена.

## 10. Границы текущей версии

REST API и web-панель не входят в 2.5.5. Telegram Admin Bot является
административным адаптером: он использует тот же `ApplicationService`, выполняет
блокирующие операции вне event loop и не дублирует lifecycle-логику плагинов.

Фундамент для web-панели уже отделён от TUI, но полноценный аналог 3x-ui требует
самостоятельного HTTP-адаптера: безопасных DTO без секретов, аутентификации,
RBAC, CSRF-защиты, audit log и явного CRUD для пользовательских inbound'ов. Эти
функции должны добавляться поверх application services, не возвращая
бизнес-логику в контроллеры.

Остальные границы версии:

- CRUD произвольных пользовательских inbound'ов не входит в plugin API;
- UDP/443 не мультиплексируется — это ограничение сетевой модели, а не
  реализации: прямым владельцем порта может быть только один QUIC-транспорт;
- Telemt не входит в подтверждённую матрицу детекторов AntiDPI;
- поддерживаются только Ubuntu и Debian с systemd.

Новый компонент может считаться частью стабильной архитектуры только когда он
подключается через прикладную службу, описывает контракт плагина, участвует в
транзакционном жизненном цикле и имеет тесты сценариев отказа.
