# AntiScan (`antidpi`)

> **Модуль:** `antidpi` · **Служба:** `hydra-antidpi` · **Роль:** AntiScan · **Актуален в:** 3.0.0

AntiScan — доказательный контур блокировки. Он банит только два класса
доказанных событий:

1. **отказ протокола** — внешний клиент дошёл до handshake-шлюза протокола и
   предъявил неверные данные;
2. **скан сайта-заглушки** — запрос пути, характерного для автоматического
   поиска уязвимостей.

Событие либо доказано целиком — протокол, настоящий внешний IP и факт
неверных данных, — либо отбрасывается в парсере. Промежуточного
«подозрительно, но не доказуемо» состояния нет.

Диапазон адресов и пути — в [REFERENCE.md](REFERENCE.md), место модуля в
оркестраторе — в [ARCHITECTURE.md](ARCHITECTURE.md).

## 1. Закрытый контракт улик

Событие становится уликой, только если одновременно выполняется всё ниже. Это
чистая проверка (`evidence_problem()` в `detection.py`), а не оценка правдоподобия.

| Условие | Требование |
| :--- | :--- |
| Вид | `protocol_reject` или `decoy_scan`; других нет |
| Владелец ошибки | Точный service/inbound tag конкретного протокола |
| Точность ошибки | Только грамматика из allowlist, не общие слова |
| Атрибуция | `direct` или `relay-exact`; временны́е догадки запрещены |
| Адрес | Публичный, не loopback, не адрес хоста, не whitelist |

Всё остальное отбрасывается до записи состояния. Парсер возвращает `None`, и
событие не существует: ни строки в истории, ни вызова firewall, ни сообщения.

## 2. Доказуемый отказ протокола

Событие `protocol_reject` означает: клиент говорил на протоколе и не смог
предъявить валидные данные. Сейчас **ни один протокол не входит в allowlist
автоматического enforcement**: единственной автоматической уликой остаётся
скан сайта-заглушки (раздел 3).

### Snell: почему не в enforcement

Snell не банится: запись `cipher: message authentication failed` одинакова для
зонда и для клиента с устаревшим PSK, а тег не сверяется с желаемым
состоянием. Запись остаётся диагностическим входом (парсер её распознаёт,
no enforcement); Snell вернётся в allowlist только с проверкой владения тегом
(раздел 12).

## 3. Скан сайта-заглушки

Событие `decoy_scan` означает: с внешнего адреса пришёл запрос к пути, который
обычный клиент не запрашивает.

Уликой считается только совпадение по нормализованному **пути** (query-строка
отбрасывается):

| Путь | Что это |
| :--- | :--- |
| `/.env`, `/.env.*` на любой глубине | поиск файла с секретами |
| `/.git/` | поиск метаданных репозитория |
| `/wp-login`, `/xmlrpc.php` | подбор входа в WordPress |
| `/actuator`, `/cgi-bin/`, `/server-status` | поиск служебных эндпоинтов |

Уликой **не** считается: произвольный `404`, обычные страницы и ассеты,
`robots.txt`, совпадение только в query-строке, один лишь HTTP-метод
(`CONNECT`/`TRACE`/`TRACK`), запрос к реальному эндпоинту протокола.

## 4. Что модуль не наблюдает

Модуль не реагирует на всё, что не привязано к доказанному внешнему адресу:
generic-ошибки TLS и `unknown_sni` на общем TCP/443, rate/scan-телеметрия ядра,
UDP-зонды, инференс Mieru по объёму, корреляция подсетей и атрибуция по
времени. UDP-транспорты (Hysteria2, qWDTT, AmneziaWG, Mieru) в источники
решений не входят: source подделывается, владелец адреса не доказан.

## 5. Протокольная матрица

| Протокол | Enforcement | Причина |
| :--- | :--- | :--- |
| **Decoy-сайты** | **включён** | явный путь сканера (`/.env`, `/.git/*`) в access-log |
| **Snell** | не поддержан | `message authentication failed` не отличает зонд от клиента с устаревшим PSK; тег не сверяется с желаемым состоянием |
| Naive | не поддержан | неавторизованного уводит на decoy, атрибутируемого отказа нет |
| AnyTLS | не поддержан | неверный пароль уходит в fallback молча |
| VLESS | не поддержан | XHTTP терминируется в Caddy, native-сервис адреса не видит |
| TrustTunnel | не поддержан | отказа в журнале нет |
| ShadowTLS | не поддержан | HMAC mismatch уходит в fallback |
| Hysteria2, qWDTT, AmneziaWG, Mieru | не поддержаны | UDP: source подделывается, владелец адреса не доказан |
| Calls | не поддержан | нет стабильного атрибутируемого отказа |

Протокол без своего адаптера не попадает даже в фильтр журнала: он не порождает
записей, которые потом отбрасываются.

```text
caddy-naive/access.log ───────┼──> строгий парсер ──> закрытый allowlist

                                         │                    │

                                    (только курсор)           │

```

Коллектор читает **один** поток журнала (`sing-box`) и файловые decoy-логи.

## 7. Политика BAN

Одна доказанная улика запускает прогрессивную лестницу:

| Нарушение | Срок |
| :--- | :--- |
| 1 | 10 минут |
| 2 | 1 час |
| 3 | 24 часа |
| 4+ | 7 суток |

Порядок применения сохраняет транзакционные гарантии:

1. намерение бана записывается в state **до** обращения к firewall, поэтому
   падение процесса лечится сверкой при старте;
2. firewall добавляет адрес в `hydra_antidpi` / `hydra_antidpi6`;
3. если firewall отказал — намерение **откатывается**, записывается
   `ban_failures`, уведомление о успехе не отправляется;
4. повторная улика по уже забаненному адресу не продлевает срок и не шлёт
   второе уведомление.

Ручной бан (`manual_ban`) и разбан остаются: бан администратора бессрочен до
снятия вручную и имеет приоритет над прогрессивной лестницей.

## 8. Whitelist

Whitelist имеет приоритет над любой уликой. Проверяются: настроенные сети,
адреса хоста и loopback. Проверка выполняется до записи состояния, поэтому
доверенный адрес не создаёт ни бана, ни истории. Баны, попавшие под whitelist,
снимаются при старте и при каждой сверке.

```bash
sudo hydra plugin command antidpi add_whitelist --param network=203.0.113.0/24
sudo hydra plugin command antidpi remove_whitelist --param network=203.0.113.0/24
```

В TUI то же самое доступно из меню AntiScan.

## 9. Уведомления Telegram

Автоматическое уведомление одно — **BAN**, когда бан применён firewall'ом.
Отказ firewall уведомления не порождает: он остаётся в состоянии
(`ban_failures`), в журнале службы и виден в ответе кнопки при ручном бане.

Сообщение о бане содержит IP и гео/владельца, вид улики, протокол, причину,
источник, метод атрибуции и срок. Оно **не содержит** паролей, UUID, токенов и
сырых строк журнала.

Отброшенный ввод не может вызвать уведомление — это проверяется тестом
(`test_discarded_input_neither_bans_nor_notifies`).

## 10. Состояние и совместимость

Файл — `/var/lib/hydra/antidpi.json`, права `0600`, запись атомарна и под
блокировкой.

| Поле | Назначение |
| :--- | :--- |
| `banned` | активные баны: причина, атрибуция, срок, нарушение |
| `ban_counts` | число нарушений по адресу для лестницы сроков |
| `history` | ограниченная история банов и их исходов |
| `ban_failures` | отказы firewall для видимости оператору |
| `whitelist` | доверенные адреса и сети |
| `reconciliation` | результат последней сверки правил и банов |
| `collector_heartbeat_at` | живость сборщика |
| `journal_cursor` | позиция в журнале, чтобы простой не терял события |
| `events`, `last_event_at`, `last_event_source` | агрегаты последнего события |

Файл может содержать поля `scores`, `subnets`, `signal_counts`, `source_counts`.
Решение по ним не принимается. `scores` сопровождается ради непрерывности offense
и улик ручного бана; `signal_counts` и `source_counts` видны в операторской
проекции как счётчики сигналов и источников (`projection.counters`).

Состояние — plugin-owned; схема `AppState` его не описывает.

## 11. Эксплуатация

### Проверка состояния

```bash
hydra plugin query antidpi management_snapshot
sudo ipset list hydra_antidpi
sudo ipset list hydra_antidpi6
sudo journalctl -u hydra-antidpi -n 100 --no-pager
```

Health объединяет: `service`, `ipsets`, `firewall`,
`obsolete_telemetry_removed`, `collector_heartbeat`, `state`, `reconciliation`.
Проверка `obsolete_telemetry_removed` подтверждает, что в firewall нет
телеметрических правил scan/UDP/Mieru.

### Экран TUI

Здесь: переключатель службы, блокировки и история с разбаном, статистика улик,
whitelist, ручная блокировка, журнал службы и локальная диагностика.

### Локальный self-test

```bash
sudo hydra antidpi selftest --output /tmp/antidpi-selftest.tar.gz
```

Тест шлёт локально неверные данные на порт Snell и проверяет, что парсер,
фильтр и архив видят один и тот же отказ. Это доказывает **работу парсера и
трубопровода**, а не право банить: Snell снят с enforcement (раздел 2). Покрыт
только Snell: остальные протоколы не имеют атрибутируемого отказа, и
«проверять» их значило бы проверять отсутствие сигнала.

Отдельно тест **не** проверяет внешнюю атрибуцию, применение firewall и доставку
в Telegram — для этого нужно окно внешнего тестирования.

### Окно внешнего тестирования

```bash
sudo hydra antidpi capture --seconds 300 --output /tmp/antidpi-capture.tar.gz
```

Собирает журнал, логи и состояние за окно и складывает в обезличенный архив:
источники, счётчики, дельту уведомлений и диагностику firewall/socket'ов.
Архив служит входом для решения, какие протоколы доказаны, а какие нет.

### Сверка и очистка

`hydra apply` и `hydra antidpi sync` идемпотентны. Сверка восстанавливает наборы,
DROP-правила и активные баны. Сверка также **удаляет** телеметрические правила
(`hydra-antidpi-scan`, `hydra-antidpi-udp-probes`, `hydra-antidpi-mieru-probes`,
цепочку `HYDRA_ANTIDPI_UDP`) и debug-хук AmneziaWG, если они есть на хосте; итог
виден в health как `obsolete_telemetry_removed`.

## 12. Как добавить протокол

Слабую эвристику вернуть нельзя — можно только доказать новый отказ.

1. Снять с бота реальную строку отказа и убедиться, что протокол печатает
   собственный отказ, а не generic-ошибку транспорта.
2. Убедиться, что в записи есть настоящий внешний адрес (прямой listener) либо
   он восстанавливается точным соответствием `протокол + порт relay`.
3. Положить обезличенный снимок в `tests/fixtures/antidpi/` и описать провенанс
   в `MANIFEST.md` (версия, команда снятия, реданкции, ожидаемая атрибуция).
4. **Доказать, что тег принадлежит текущему желаемому состоянию HYDRA.**
   Грамматика привязывает тег из журнала, поэтому без этой проверки под неё
   попадает осиротевший или чужой listener. Сверка должна идти в журнальном
   нормализаторе (`agent._normalize_journal_record`) — единственном слое с
   доступом к состоянию. **Сейчас она не реализована**, поэтому ни один
   протокол не возвращается в allowlist.
5. Добавить грамматику в `adapters._PROTOCOL_REJECTS` и запись в
   `detection.PROTOCOL_REJECT_RULES`, плюс негативные снимки рядом — включая
   снимок «точный отказ на неучтённом теге».
6. Добавить цель в `selftest_targets.SUPPORTED_PROTOCOLS`, если протокол
   слушает напрямую.
7. Обновить матрицу в разделе 5 — включить протокол или явно оставить
   «не поддержан» с причиной.
8. Если протокол уже был в allowlist и снят — записать причину снятия рядом с
   пустым `PROTOCOL_REJECT_RULES`, а не только в матрице.

Синтетическая строка, придуманная для теста, основанием не является: она не
доказывает ни формат боевого лога, ни атрибуцию адреса.

## 13. Что модуль не обещает

- Реагировать на шум интернета и находить сканирование по rate-телеметрии:
  IP-источник на kernel-уровне подделывается, а владелец адреса не доказан.
- Учитывать легитимного клиента с устаревшим ключом: он выглядит как неверные
  данные, потому что ими и является.
- Заменять honeypot, Fail2ban для SSH и защиту провайдера от DDoS; считать
  GeoIP/ASN доказательством — это справочная информация для оператора.
