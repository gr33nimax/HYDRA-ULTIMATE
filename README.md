HYDRA разворачивает и обслуживает многопротокольный прокси-сервер на одной VPS.
Десять транспортов, маршрутизация, DNS, защитные контуры, подписки, учёт трафика
и интерфейсы TUI/CLI/Telegram работают как единый управляемый контур.

Вручную конфигурации служб не редактируются: пользователи, протоколы и сеть
описаны в одном `state.json`, из которого генерируются конфигурации Sing-Box,
Caddy L4 и nftables. Применение — транзакционное, с проверкой и автоматическим
откатом.

> [!IMPORTANT]
> `2.5.4` — текущая версия ветки `dev`. Проект в активном бета-тестировании.
> Для рабочей эксплуатации используйте чистый Ubuntu 20.04+ или Debian 11+ и
> обязательно настройте резервное копирование.

## Зачем это нужно

Тот же результат достижим вручную — Sing-Box, Caddy, certbot, nftables, ipset,
Fail2ban, systemd-units и скрипты учёта трафика. Проблема не в первичной
настройке, а в том, что происходит при каждом последующем изменении.

| Что ломается вручную | Что делает HYDRA |
| :--- | :--- |
| Сменили домен — state и Caddy разошлись, доменные транспорты недоступны | Домены — производная от state; расхождение SNI видно как блок `tls_mux` и лечится повторным `apply` |
| Правка применилась наполовину: Sing-Box перезапущен, nftables нет | Каждый изменяющий шаг имеет снимок и rollback; при сбое возвращаются state, конфигурации, firewall и плагины |
| Два QUIC-транспорта незаметно заняли UDP/443 | Конфликт слушателей отклоняется до применения, а не проявляется отказом в рантайме |
| Служба показана «включённой», хотя не работает — или наоборот | Желаемое и фактическое состояния разделены; `status` показывает оба и расхождение |
| Обновление сводится к `git pull` с риском отдать старому коду новую схему state | Транзакционный updater: новый release рядом с рабочим, preflight, два уровня backup, атомарное переключение, откат |
| Новый пользователь добавлен в один транспорт и забыт в остальных | Добавление пользователя — транзакция по всем включённым транспортам |
| Сканирование и protocol probes ловятся разрозненно, ложные баны блокируют своих | Единый контур корреляции с двухуровневым scoring; UDP-сигналы не дают автоматический бан |

## Ключевые свойства

- **Единый источник истины.** `state.json` содержит только желаемую и
  долговечную конфигурацию; факты рантайма туда не пишутся.
- **Транзакционное применение.** Снимок, rollback в обратном порядке, журнал
  `apply.jsonl`, повторный запуск как штатный сценарий.
- **Контролируемый TLS.** Сертификаты проверяются на домен, срок и соответствие
  ключу до применения; Caddy не получает маршрут без полной проверенной пары.
- **Обновление без потери доступа.** Останавливаются только службы HYDRA;
  Sing-Box и внешние прокси-бинарники updater не заменяет.
- **Headless-управление.** В терминале CLI показывает понятные сводки и таблицы,
  а `--json` даёт стабильный контракт для cron, systemd и внешней автоматизации.
- **Плагинная модель.** Транспорт объявляет свои возможности декларативно; общие
  службы не содержат ветвлений по имени плагина.

## Быстрый старт

### Требования

- Ubuntu 20.04+ или Debian 11+ с systemd;
- Python 3.10+;
- от 512 МБ RAM и 2 ГБ диска;
- внешний IPv4 и права `root`.

### Установка

```bash
curl -fsSL https://raw.githubusercontent.com/gr33nimax/HYDRA-ULTIMATE/main/bootstrap.sh | sudo bash
```

Установщик подготавливает зависимости, Sing-Box Extended, изолированное
Python-окружение и команду `hydra`. Caddy L4 и конкретные протоколы активируются
только при включении соответствующих модулей.

Ветку можно выбрать переменной `HYDRA_REF`. Запуск из исходников для разработки
описан в [docs/UPGRADE.md](docs/UPGRADE.md).

### Первые шаги

```bash
sudo hydra                 # интерактивный TUI: включить протоколы и службы
sudo hydra user add alice  # создать пользователя во всех включённых транспортах
hydra status               # желаемое и фактическое состояние
hydra check                # валидация и предпросмотр незавершённых изменений
```

Протоколы включаются в TUI, потому что большинству из них нужен интерактивный
ввод: домен, режим обфускации, выбор портов. Дальнейшая эксплуатация полностью
доступна из CLI.

Клиентские профили и ссылки выдаются через сервер подписок и экраны
пользователей в TUI; те же данные читаются командой
`hydra plugin query <плагин> <запрос>`.

### Обновление работающей VPS

> [!WARNING]
> Не запускайте `bootstrap.sh` поверх рабочей установки и не обновляйтесь
> вручную через `git pull`.

```bash
curl -fsSL https://raw.githubusercontent.com/gr33nimax/HYDRA-ULTIMATE/dev/updater.sh | sudo bash
```

Короткий `updater.sh` полностью скачивает транзакционный `upgrade.sh` во
временный файл и только после успешной загрузки запускает его. Updater фиксирует
точный commit ветки, собирает новую версию и `.venv` отдельно, выполняет
read-only preflight, останавливает только службы HYDRA, сохраняет проверенный
backup и исходный state, мигрирует схему, переключает release и проверяет
запуск. При любой ошибке state, код, wrapper и ранее активные службы
восстанавливаются автоматически.

Требования, состав снимка отката и процедура ручного восстановления —
[docs/UPGRADE.md](docs/UPGRADE.md).

## Поддерживаемые модули

Модули — это плагины: они объявляют свои возможности, зависимости, конфликты и
backup-ресурсы декларативно. Инвентарь доступен командой `hydra plugin list`.

### Транспорты

| Модуль | Порт по умолчанию | Назначение |
| :--- | :--- | :--- |
| **AmneziaWG 2.0** | `51820/udp`, `51821/udp` | WireGuard с расширенной обфускацией и TPROXY |
| **AnyTLS** | `443/tcp` | TLS-подобный обфусцированный туннель |
| **TrustTunnel** | `443/tcp`, `443/udp` | TLS-транспорт TCP/QUIC с сайтом-заглушкой Caddy |
| **ShadowTLS** | `443/tcp` | ShadowTLS v3 с Trojan detour |
| **NaiveProxy** | `443/tcp`, `443/udp` | Прокси HTTP/2 на базе Caddy forward-proxy |
| **Hysteria2** | `8443/udp` | QUIC с Salamander и браузерной заглушкой |
| **Mieru** | `2012–2022/tcp` | Обфусцированный mTLS-транспорт, ссылки `mierus://` |
| **Snell v4** | `32000–32999/tcp` | TCP/UDP-прокси из Sing-Box Extended |
| **MTProto / Telemt** | `8443/tcp` | Telegram MTProxy с управлением пользователями |
| **qWDTT** | `56000/udp`, `56001/udp` | WireGuard-туннелирование поверх TURN |

TCP/443 разделяется между несколькими TLS-транспортами через мультиплексор
Caddy L4 по SNI. UDP/443 по SNI не распределяется: его прямым владельцем может
быть только один QUIC-транспорт.

### Сетевые расширения

| Модуль | Назначение |
| :--- | :--- |
| **DNSCrypt** | Локальный шифрованный DNS-резолвер на `127.0.0.1:5300` |
| **WARP** | Выборочная маршрутизация через Cloudflare WireGuard, RU/IDN-списки |

### Защита

| Модуль | Назначение |
| :--- | :--- |
| **AntiDPI** | Корреляция protocol probes и сканирования, динамический ipset с прогрессивным TTL |
| **Fail2ban** | SSH и аутентификационные журналы |
| **Honeypot** | Ловушка на выделенном порту `9999/tcp`, собственные баны |
| **IPBan** | Статические списки IP/CIDR/ASN/стран |

Учёт трафика, применение лимитов и сроков пользователей выполняет служба
`hydra-traffic-daemon` — это часть ядра, а не плагин.

Полная карта портов, служб и файлов — [docs/REFERENCE.md](docs/REFERENCE.md).

## Как это работает

### Слои

Управляющие интерфейсы никогда не обращаются к хосту напрямую. TUI, CLI и
Telegram — тонкие адаптеры над одним набором прикладных служб.

```text
TUI · CLI · Telegram · будущие API-адаптеры
                 │
                 ▼
   ApplicationService и прикладные порты
                 │
                 ▼
ConfigurationApplier · PluginLifecycle · UserLifecycle
                 │
                 ▼
HostBackend → systemd · Sing-Box · nftables · Caddy L4 · файлы
```

Все привилегированные операции проходят через единый `HostBackend`: argv без
shell, с таймаутом и сокрытием секретов. Это граница, которую удерживают
архитектурные тесты, а не соглашение.

### Путь изменения

```text
state.json
   │  проверка и миграция схемы
   ├─ сбор ConfigFragment от включённых плагинов
   ├─ генерация и валидация конфигурации Sing-Box
   ├─ применение nftables / TPROXY
   ├─ применение включённых плагинов
   ├─ перезагрузка Sing-Box
   ├─ пересборка и проверка Caddy L4 (если требуется)
   ├─ согласование службы учёта трафика
   ├─ проверка работоспособности
   └─ фиксация или откат в обратном порядке
```

Плагин не редактирует итоговый `config.json`: он возвращает типизированный
`ConfigFragment` (inbounds, outbounds, правила маршрутизации, DNS, TPROXY-порты),
который проходит валидацию и общую проверку конфликтов слушателей.

### Желаемое и фактическое

`state.json` хранит только намерение. Факты — `running`, `health`, расхождение —
вычисляются отдельно и никогда не записываются в state как истина. Поэтому
«выключено» в state и работающая служба на хосте не противоречат друг другу: это
рассинхронизация, которую показывает `hydra status` и устраняет `hydra apply`.

Запись state атомарна, с backup, fsync и монотонной `revision`: устаревшая
запись желаемой конфигурации отклоняется как конфликт, а не затирает более новое
изменение другого процесса.

> [!WARNING]
> Не исправляйте фактическое состояние правкой `state.json`. Сначала выясните
> причину расхождения через `hydra status` и `hydra check`.

### TLS как отдельный артефакт

TLS-маршруты вынесены в отдельный проверяемый контур, потому что ошибка в них
означает одновременную потерю доступа ко **всем** доменным транспортам. Перед
применением проверяются SAN, остаточный срок действия и соответствие приватному
ключу; маршрут с завершением TLS не рендерится без полной проверенной пары.

Подробности — [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md).

## Эксплуатация

### Повседневные команды

```bash
hydra status                 # желаемое и фактическое состояние, блок tls_mux
hydra check                  # валидация, предпросмотр изменений, готовность хоста
sudo hydra apply             # транзакционное применение
sudo hydra backup create     # проверяемый архив state и конфигураций
hydra plugin list            # инвентарь модулей и их возможностей
```

Команды чтения не требуют `root` и не меняют систему. В терминале вывод
человекочитаемый; для автоматизации используйте `--json` и
`error_details.code`, а не текст ошибки.

Формы предыдущих релизов (`validate`, `plan`, `doctor`, `reconcile`) сохранены
как алиасы и сводятся к `hydra check`.

### Безопасный порядок изменения

```bash
sudo hydra backup create --output /root/hydra-before-change.tar.gz
hydra check
sudo hydra apply
hydra status
```

### Управление пользователями

```bash
sudo hydra user add alice --traffic-limit-gb 100 --expiry-date 2026-12-31
sudo hydra user set-device-limit alice 3
sudo hydra user block alice
sudo hydra user rename alice alice@example.com   # UUID и секреты сохраняются
hydra user list                                  # без секретов
```

Лимит трафика и срок действия применяются независимо от ручной блокировки:
исчерпанный лимит отключает доступ без `block`, а `unblock` не вернёт доступ,
пока ограничение действует.

### Если что-то сломалось

```bash
hydra status
hydra check
sudo journalctl -u sing-box -u caddy-l4 --no-pager -n 100
sudo hydra apply                     # повторный запуск — штатный сценарий
```

Если конфигурация повреждена, восстановление идёт из архива:

```bash
sudo hydra backup restore /root/hydra-before-change.tar.gz --dry-run
sudo hydra backup restore /root/hydra-before-change.tar.gz --yes
sudo hydra apply
```

Полный справочник команд, параметров и кодов ошибок — [docs/CLI.md](docs/CLI.md).

## Безопасность

- Секреты не попадают в публичный статус, human/JSON-вывод CLI и диагностические
  архивы: известные пароли, токены, UUID, PSK и приватные ключи заменяются на
  `[REDACTED]`.
- Backup и restore работают только по доверенной policy: абсолютные scoped-пути,
  манифест, размер, SHA-256, защита от traversal, симлинков и дубликатов; перед
  восстановлением создаётся страховочная копия.
- Токен Telegram-бота — **root-equivalent секрет**. Бот работает от `root`; не
  добавляйте его в группы и перевыпускайте токен при подозрении на компрометацию.
- AntiDPI устроен так, чтобы сомнительное событие уведомляло оператора, но не
  блокировало адрес без проверенного доказательства. Прямые UDP-сигналы
  автоматический бан не дают — иначе подделанный source IP позволил бы
  заблокировать чужой адрес.

Чего система не обещает: обнаружения любой атаки, защиты от украденных
credentials, различения клиентов за одним NAT и фильтрации объёмного DDoS —
последнее должно выполняться у провайдера до VPS. Подробнее —
[docs/ANTIDPI.md](docs/ANTIDPI.md).

## Ограничения текущей версии

- REST API и web-панель в `2.5.4` не входят. Фундамент отделён от TUI, но
  полноценный HTTP-адаптер требует DTO без секретов, аутентификации, RBAC,
  CSRF-защиты и audit log.
- CRUD произвольных пользовательских inbound'ов не является частью plugin API.
- UDP/443 не мультиплексируется — это ограничение сетевой модели, а не реализации.
- Telemt не входит в подтверждённую матрицу детекторов AntiDPI.
- Поддерживаются только Ubuntu и Debian с systemd.

## Разработка

```bash
python verify.py                                    # compile + lint + полный pytest
python -m pytest -q                                 # только тесты
python -m ruff check main.py hydra tests            # только линтер
python -m compileall -q main.py hydra               # только компиляция
```

Тесты — часть архитектуры: помимо обычных проверок они удерживают направление
зависимостей, отсутствие циклов в import graph, лимиты размеров модулей и
функций и запрет обхода `ApplicationService` и `HostBackend`. Ослаблять
архитектурный guard, чтобы «починить тест», нельзя.

CI проверяет Python 3.10–3.13, зависимости (`pip-audit`), миграции состояния,
Linux-сценарий с root/systemd/nftables и транзакционное обновление `main → dev`.

Правила расширения, декларация возможностей плагина и обязательный набор тестов —
[docs/PLUGIN_DEVELOPMENT.md](docs/PLUGIN_DEVELOPMENT.md).

## Структура проекта

```text
HYDRA-ULTIMATE/
├── main.py                 # точка входа в интерактивный TUI
├── bootstrap.sh            # установка и подготовка новой VPS
├── updater.sh              # однокомандный запуск обновления
├── upgrade.sh              # транзакционное ядро updater
├── verify.py               # локальная проверка: compile, lint, тесты
├── hydra/
│   ├── contracts/          # нейтральные типизированные контракты
│   ├── core/               # state, Sing-Box, nftables, Caddy L4, host
│   ├── plugins/            # транспортные, сетевые и защитные плагины
│   ├── services/           # прикладные use-cases, учёт, подписки, синхронизация
│   ├── ui/                 # TUI и модули представления
│   └── entrypoints/        # тонкие адаптеры фоновых служб
├── docs/                   # техническая документация
└── tests/                  # автоматические проверки
```
